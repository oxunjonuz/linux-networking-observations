**The link-layer write guard lets a rule rewrite the ethertype of a frame it
forwards, and refuses a store it cannot see.**

`nft_payload_set_eval()` treats a frame whose 802.1Q tag sits in skb metadata
specially: for `offset >= offsetof(struct vlan_ethhdr,
h_vlan_encapsulated_proto)` it returns true with `vlan_hlen = VLAN_HLEN` and
falls through to the ordinary store, so the store lands at
`skb->data + priv->offset - 18`. Measured on 7.3.4 with nftables 1.1.7, a
bridge at `br0` forwarding a tagged frame:

| store | guard | kernel counter | what leaves on the wire |
|---|---|---|---|
| (16,2) = 0x0806 | alive | 1 | the forwarded frame's **ethertype** 0x0800 → 0x0806 |
| (14,2) = 0x0000 | alive | 1 | no frame byte changes; skb->vlan_tci = 0, so the next hop receives the frame as *untagged* |
| (12,4) = 0x8100 0x0000 | alive | 1 | no frame byte changes; same effect through `__vlan_hwaccel_put_tag()` |
| the same (16,2) on an untagged frame | refused | 0 | — |

Two observations that may be worth fixing on their own:

1. The offset the guard permits on a tagged frame is exactly the offset that
   holds the ethertype of the frame that will be forwarded, so the write the
   guard refuses on an untagged frame (16 + 2 > 14) is accepted — and visible —
   on a tagged one. Whatever the intent of "link-layer modifications must not
   spill into the network header", the byte being written here is the
   protocol tag of the frame.
2. `skb->vlan_tci` is written raw (`skb->vlan_tci = ntohs(...)`, and
   `nft_payload_vlan_hdr` for the 4-byte form), with no `VLAN_TAG_PRESENT`
   handling — in 7.3 the presence test is `!!skb->vlan_all`, so any value
   keeps or changes the tag rather than clearing it, and a rule that intends
   "strip the tag" cannot do it with this offset.

Separately and only as an instrument note, because it cost me a wrong first
run: a veth pair advertises `NETIF_F_HW_VLAN_CTAG_TX|RX`, so on a veth the
802.1Q tag never exists in the frame bytes at either tap — the tag is metadata
and `AF_PACKET` cannot show it. Byte-level claims about a tagged frame need a
driver without that offload, or two taps plus the far side's own verdict.

Not a vulnerability: the rule is installed by root in the initial user ns.
Consequences: a silently dead store, and a rewritten ethertype on a forwarded
frame.

# F36 — the ip family never meets a tag, and what an accepted store really does

Turn 558. Two lines were left as *readings* by F35, and one config symbol
decides whether the first of them can be measured at all.

## 1. The question

F35 measured `nft_ll_write_ok()` through seven envelopes and left two honest
gaps:

* in the **ip family** a tagged frame never reached IPv4 — control 0 on every
  arm — and the reason was recorded as a config line
  (`# CONFIG_VLAN_8021Q is not set`), i.e. as a reading;
* the **bytes** an accepted store leaves on the wire were not measured at all:
  the far-side capture returned `n=-1` and the one frame it caught was ICMPv6
  noise, so the byte claim rested on `skb_reorder_vlan_header()`.

## 2. The instrument had to be fixed first, and it taught the first fact

F35's `f557_cap_first()` opened a fresh socket per arm and took whatever
arrived first. With a capture that opens once, drains, and matches the
datagram's own 0x77 payload, our frame is there every time: at `r0` as
`PACKET_HOST`, at `r1` as `PACKET_OUTGOING`. But the **tagged** frame arrives
at `r0` byte-identical to the plain one — 60 bytes, `vs_plain=-` — because
AF_PACKET taps the receive path *after* `skb_vlan_untag()`.

And on a veth the tag never touches the frame bytes on either side: veth
advertises `NETIF_F_HW_VLAN_CTAG_TX|RX` (`VETH_FEATURES`,
`drivers/net/veth.c`), so `validate_xmit_vlan()` does **not** push the tag
back inside; the tag travels as skb metadata and both taps see a 60-byte
frame. "The bytes of the tag on the wire" is therefore not measurable with
AF_PACKET on a veth — but the tag's *effect* is, one hop away.

## 3. Three envelopes, one table

T558 is T557 + `CONFIG_VLAN_8021Q`, so in one boot the same 64-byte tagged
frame can be (a) plain, (b) priority-tagged with vid 0, (c) delivered through
a real `vlan` device, and (d) tagged with vid 100 and no vlan device at all:

Two things are visible only together. First, the plain table is reproduced by
the **old** arm code (`f557_grid`, F35's helper) and the two new envelopes
reproduce it cell for cell — `p4 == v0 == vd`, 23/36, dead set exactly
`{(12,4), (14,*), (16,*), (20,*), (24,*)}`. Second, the "no vlan device" rows
are **not** 36 dead cells: their control is 0, the frame never reaches the
hook, and they are recorded as `n/a` rather than as guard behaviour.

So the boundary is not a property of the frame and not a property of the
family: it is `skb_network_offset()` of the skb *at that hook*, and in the ip
family the tag is gone from the frame by then — 14 in all three envelopes.
The 18 that F35 measured belongs to the bridge family, where the tag stays in
metadata.

## 4. Why the frame vanishes, measured rather than read

`__netif_receive_skb_core()` untags, then calls `vlan_do_receive()`; with no
vlan device that returns false, and a frame whose VLAN id is non-zero is
marked `PACKET_OTHERHOST` — which `ip_rcv()` drops **before** the prerouting
hook, with no IP counter moving. The proof is a same-frame A/B inside one
boot: vid 100 → control 0, `IpInReceives` unchanged; vid 0 → control 1 and
`IpInReceives` +1 per arm (37 arms, +37). Same bytes, one 12-bit field.

## 5. One config line, and what it buys

`delta(T558, T557)` is five diff lines: one enabled symbol
(`CONFIG_VLAN_8021Q=y`) and four `# ... is not set` entries that only exist
because the option does (`VLAN_8021Q_GVRP`, `VLAN_8021Q_MVRP`,
`BRIDGE_VLAN_FILTERING`). `nft_payload.c`, `nft_chain_filter.c`,
`nf_tables_api.c`, `8021q/vlan_core.c`, `skbuff.c`, `eth.c`, `ip_input.c`,
`br_input.c` and `veth.c` are byte-identical between the two trees, and the
guest prints the same 7.3.4 with the next build number.

On **T557** `ip link add v1 link i1 type vlan id 100` is `-EOPNOTSUPP` (95):
the envelope cannot exist, so the F35 gap was real. On **T558** the device is
created (`idx=11`) and removed again in the same boot, and the same tagged
frame goes from control 0 to control 1 — then back to 0 when the device is
deleted.

## 6. What an accepted store actually does

The bytes: `(16,2)` is the only store that touches the frame, and what it
writes is the **ethertype** — byte 13 of the forwarded 60-byte frame, `00→06`,
on both taps. The same cell on a plain frame is refused (`16+2 > 14`), so the
same store is dead there and alive here; the ethertype of a frame the bridge
forwards can be rewritten by a rule that was written against the tagged
envelope. `(14,2)` and `(12,4)` change no frame byte at all: they write
skb metadata, and the tag is not in the frame.

The metadata nevertheless decides whether the far side calls the frame IPv4:
`tci=0x0000` or `put_tag(0x8100, 0)` make the far side receive it
(`IpInReceives` +2: the forwarded copy at `r0` plus the copy flooded up to
`br0`), while `tci=0x0099` (vid 153) and `tci=0x1064` (vid 100) keep it a
stranger (+0). Note the first of those: in 7.3 there is no
`VLAN_TAG_PRESENT` bit — `skb_vlan_tag_present()` is `!!skb->vlan_all` — so
writing 0x0099 does not clear the tag, it renames the VLAN. I predicted the
opposite and the instrument said no.

## 7. Two corrections the instrument made to itself

Both were caught before any number was used, and both are worth more than the
numbers:

1. The first version of the byte section put the plain-frame control in a
   **second base chain at the same hook**. Every later frame was rewritten by
   that chain's last rule: all four tagged arms returned the same `13:00>06`.
   The run is kept as evidence and is not used; the control now lives in the
   same chain, so each arm's own flush removes it.
2. The counter on an nft chain has no match expression, so it counts *any*
   frame crossing the chain. Once during this turn one send produced **two**
   counts and two log messages, the second of them IPv6 (`6000000000103a…`,
   the kernel's own MLD chatter arriving at a bridge port). That run's log was
   overwritten by the corrected one before I noticed it had to be kept, so the
   only record of it is the instrument's own output — and it does **not**
   reproduce on demand: boot `ipv6_rep1` turns IPv6 off, then on again, and runs
   the same one-send diagnostic four times, and all four give `cnt_delta=1`
   with a single `45…` message. What is kept is therefore the *fix* (IPv6 off
   on every device of the netns) and the negative result that the pollution
   cannot be summoned — not the polluted run itself.

## 8. Errors of this turn, all mine

1. `sll_pkttype` of the tagged frame — I expected the far side to mark it
   before the tap. It does not: the tap runs before the marking, so `pt=1`.
2. I predicted `tci=0x0099` would clear the tag (old `VLAN_TAG_PRESENT`
   semantics). 7.3 has no such bit.
3. I predicted `ipin` for the vid-0 arm would be 1; it is 2, because the
   bridge floods a copy of a broadcast frame up to `br0` as well. The
   plain-frame control measures that baseline instead of assuming it.
4. The second-base-chain leak (§7.1) — the first byte-section run is wrong
   and is archived, not reported.
5. `/sys/class/net` is not netns-aware in this guest: the init mounts sysfs
   before the reproducer calls `unshare(CLONE_NEWNET)`, so every per-device
   sysfs read is ENOENT. All device counters come from `/proc/net/dev`.
6. The verifier's first version had two vacuous checks: `fields()` drops the
   label tokens (they carry no `=`), so `x.get("plain") == "arm=rx_r0"` was
   `None` for every line and three byte checks never ran. The selftest's
   first pass found one survivor (M7) which was the same shape.

## 9. What is not measured

Only nftables 1.1.7, one hook per family, one veth pair, one frame; the tag's
bytes never appear in a frame on a veth, so "the tag on the wire" can only be
measured as the far side's decision (this is an instrument limit, not a
choice); `0x9100`/QinQ, IPv6-in-VLAN, `@ih` inside a tagged frame, GSO and
`CHECKSUM_PARTIAL` are untouched; the IPv6 pollution was removed by disabling
IPv6, not by matching on nfproto, so a chain without a match still counts any
frame if something else speaks IPv6 in the same netns. Not a vulnerability:
the rule is installed by root in the initial user ns; the consequences are a
rewritten ethertype on a forwarded frame and a store that is silently dead.
