STATUS: NOT SENT. Follow-up to the F28 report; no patch is proposed.

Theme: the guard for a payload store is selected by the *chain's* family and the
*hook number*, and the checksum fixup has a guard of its own that fails silently.
All numbers below are measured on 7.3.4 over two boots, 63 arms, one rule per
arm, six hooks (`netdev` ingress on a veth, `inet` ingress on the same device and
the same hook point, `ipv4`/`ipv6`/`inet` prerouting, and the native `arp`
family at `NF_ARP_IN`), with the frame's bytes read back after the store through
NFLOG, the datagrams counted at a bound socket, and -- for ARP -- what the kernel
learned read back from the neighbour table.

1. Two chains on one ingress hook point get two different guards.

   nft_ll_write_ok() and nft_nh_write_ok() both test
   `pkt->state->pf`/`pkt->state->hook`, and nft_do_chain_inet_ingress()
   rewrites `state->pf` from NFPROTO_NETDEV to the packet's family before the
   chain runs:

       pf = NFPROTO_NETDEV, hook = NF_NETDEV_INGRESS:  @ll unbounded, @nh unbounded
       pf = NFPROTO_IPV6,   hook = NF_INET_INGRESS:   off+len <= 14, ip6 whitelist

   Same device `x1`, same frame, same hook point:

       @ll,14,2  netdev: written (frame byte 14) -> Ip6InHdrErrors 1,
                 Ip6InReceives 0, no delivery
       @ll,14,2  inet:   refused (counter 1, no log message), delivered
       @ll,16,2  netdev: written;                     inet: refused
       @nh,6,1   netdev: written -> Ip6InUnknownProtos 1, no delivery
       @nh,6,1   inet:   refused -> delivered

   Note `Ip6InReceives 0` with `Ip6InHdrErrors 1`: the frame died inside the
   ingress hook (`nft_set_pktinfo_ipv6_ingress()` checks `ip6h->version`),
   before ip6_rcv_core() where IPSTATS_MIB_IN is counted.

2. The IPv4 `@nh` whitelist, measured whole (ipv4 prerouting):

       (0,2) accepted only if the version|ihl octet is unchanged; (0,2) with 55
       refused; (1,1) yes, (1,2) no; (4,2) yes, (4,1) no; (8,1) yes; (8,2) yes
       only if the protocol byte is unchanged; (10,10) yes, (10,11) no;
       (12,8) yes, (12,9) no; (16,4) yes, (16,5) no; (20,2) no.

   `(12,8)` writes saddr+daddr and kills the datagram at the UDP checksum
   (UdpInErrors 1) while IpInHdrErrors stays 0; `(10,10)` rewrites the checksum
   field, both addresses and the frame is routed nowhere without a counter.

3. The ARP guard compares a length, never an end.

       nft_nh_write_ok_arp(): offset >= 8 && len <= 20, plus (6,2) for ar_op.

   The message is 28 bytes. Accepted and written: (8,6) -> the kernel learns
   10.59.0.11 -> a0:a1:a2:a3:a4:a5; (14,4) -> the sender address is rewritten,
   so the entry appears under 10.59.0.77 instead; (24,4) -> the target is no
   longer us and nothing is learned at all; (27,2) and (27,14) -> accepted and
   written past the message, into the ethernet padding of the same frame.
   Refused: (6,1), (7,2), (8,21).
   (27,20) is the separating cell: the guard says yes, `skb_ensure_writable()`
   says no (27+20 > 46-byte skb), so the counter counts and nothing is written.

4. `csum type inet` is not one thing, and where its guard says no it says
   nothing.

       nft_payload_set_eval():
           if (csum_type == INET && nft_payload_csum_write_ok(pkt, priv) &&
               nft_payload_csum_inet(...)) goto err;

   A false guard skips the fixup and lets the store happen.

   * `@nh` in ipv4: the fixup repairs the IPv4 header checksum -- which is
     validated in ip_rcv_core(), i.e. BEFORE a prerouting store. Writing saddr
     without the fixup leaves IpInHdrErrors 0 and the datagram dies at the UDP
     checksum instead. At the *ingress* hook the same write without the fixup
     is fatal (IpInHdrErrors 1, no delivery) and with it the datagram is
     delivered: the same attribute is worthless at one door and decisive at
     the other.
   * `@nh` in ipv6: nft_payload_csum_nh_write_ok() is false, the 16-byte source
     address store is applied and the UDPv6 checksum is left stale
     (Udp6InErrors 1); the same intent spelled `csum_flags=1` (pseudo-header
     update) is delivered.
   * `@th` with a UDP datagram whose checksum field is 0 (legal in IPv4):
     `csum type inet` reads 0 and writes a non-zero value that is not the
     checksum of the modified datagram -> UdpInErrors 1; `csum_flags=1` skips
     the datagram (`nft_payload_l4csum_offset()` returns -1) and it is
     delivered; no fixup at all is also delivered.
   * Three load-time refusals, invisible to the counter because the rule does
     not exist: `csum type inet` on base ll, `csum type inet` with
     `csum_offset != 10` on `@nh` in family ipv4, and `csum type inet`
     together with `csum_flags` on `@th` (-EINVAL).

5. `inet` at prerouting is `ip`/`ip6`; `inet` at ingress is a third thing.
   At prerouting `state->pf` is the packet's family (one ops registered in both
   hook lists), so the four prerouting cells (ipv4 vs inet, with and without
   the fixup) agree exactly. The odd door is ingress, not the family.

6. An empty `inet` ingress chain is not a no-op: it runs
   nft_set_pktinfo_ipv6_ingress() before the first rule, and that parses the
   extension header chain. A frame with a broken destination-options header
   reaches the ipv6 prerouting hook when the table is absent (probe 1) and does
   not when it is present (probe 0, Ip6InHdrErrors 1, Ip6InReceives 0). With a
   broken hop-by-hop header both configurations die in ip6_rcv_core() -- which
   is where the hop-by-hop walk lives -- and only Ip6InReceives tells them
   apart.

Not measured here: a real socket path (skb->ip_summed == CHECKSUM_PARTIAL), on
which the `@th` fixup is deliberately skipped; TCP/ICMP csum_offset; SCTP; IPv4
with options; @nh with csum on the netdev ingress door. All rules were installed
by root in the initial user namespace, which F57 measured to be the only context
where a packet store is accepted at all.

# F59 — страж принадлежит цепочке, а поправка — пакету

**Вопрос хода** (три долга, названные в §10 F58): списки `@nh` для **IPv4 и
ARP**, запись `@th` с **пересчётом контрольной суммы** (`csum_type` /
`csum_flags` — в F58 все плечи были `CSUM_NONE`) и семья **`inet`** на обеих
дверях.

**Короткий ответ.** Все три долга оказались одним вопросом: *кто* решает, что
запись разрешена. Страж `@ll`/`@nh` — это `nft_ll_write_ok()` и
`nft_nh_write_ok()`, и обе читают `pkt->state->pf` и `pkt->state->hook`, то есть
**семью и точку хука, а не пакет**. На одном и том же хуке `ingress` одного и
того же устройства цепь `netdev` получает безусловное «да», а цепь `inet` —
арифметическую границу и белый список, потому что `nft_do_chain_inet_ingress()`
переписывает `state->pf` в семью пакета, а `nft_in_ingress()` проверяет
`pf == NFPROTO_NETDEV`. Поправка суммы — второй такой случай: у `csum_type=INET`
на базе `@nh` свой страж (`nft_payload_csum_nh_write_ok()`), который говорит
«только IPv4», и **ложное «нет» там не отказ, а молчание**: фиксация не
делается, запись делается.

Ядер не собирал: всё на том же `7.3.4-T563` (`1efbc957…2033`).

## 1. Прибор и топология

`differ581`, режим `guard` — **63 плеча в каждой из двух загрузок**, одно
правило на плечо `counter, [запись], log(81), accept`. Загрузки совпадают
построчно после нормализации — а нормализовать нечего: все 63 строки и обе
строки `BAD` совпали поле в поле (включая каждый байт каждого hexdump).

Пара veth `x0↔x1`; на `x1` — IPv6 `fd02::91/64` с сокетом UDP6
`fd02::91:5000` и IPv4 `10.59.0.1/24` с сокетом UDP4 `10.59.0.1:5000`;
ARP включён.

**Шесть дверей** (у каждой своя таблица и цепь `c0`):

| id | семья | хук | прио | что это |
|---|---|---|---|---|
| 0 | `netdev` | 0 (`NF_NETDEV_INGRESS`) на `x1` | 0 | ingress без стража |
| 1 | `inet` | 5 (`NF_INET_INGRESS`) на `x1` | 10 | **та же точка хука**, другая семья |
| 2 | `ipv6` | 0 (`NF_INET_PRE_ROUTING`) | 0 | дверь layer-3 |
| 3 | `ipv4` | 0 (`NF_INET_PRE_ROUTING`) | 0 | дверь layer-3, IPv4 |
| 4 | `arp` | 0 (`NF_ARP_IN`) | 0 | родная семья ARP |
| 5 | `inet` | 0 (`NF_INET_PRE_ROUTING`) | 0 | `inet` на layer-3 |

Плюс постоянная цепь-свидетель на `ipv6` prerouting (прио 20): она пишет в лог
каждый кадр, дошедший до layer-3, префиксом `PR`.

Пять кадров: **F1** IPv6/UDP 80 B (`fd02::11 → fd02::91`, 43580 → 5000,
18 × `0x77`); **F2** IPv4/UDP 60 B (`10.59.0.11 → 10.59.0.1`, суммы верны);
**F3** тот же с **нулевой** UDP-суммой; **F4** ARP-запрос «кто 10.59.0.1, скажи
10.59.0.11», добитый до 60; **F5/F6** IPv6 с **сломанной цепочкой расширений**
(`next header` 0 = hop-by-hop и 60 = destination options, затем `hdrlen 255`).

Свидетели: счётчик правила, сообщение NFLOG (заголовок от `mac_header`, `L2HDR`
на ingress, груз от `skb->data`), счётчики `Ip6*`/`Udp6*` и `Ip*`/`Udp*`,
сокеты UDP6/UDP4, и **таблица соседей** для ARP-плеч.

Тело ARP — 28 байт: 8 заголовка, затем SHA (8..13), SPA (14..17), THA (18..23),
TPA (24..27). Страж разрешает **любое** смещение ≥ 8 с длиной ≤ 20 и **ни разу
не сравнивает `offset + len` с 28**:

* `27,2` и `27,14` приняты и записаны — во-первых, последний байт TPA,
  во-вторых, 14 байт **за** телом ARP (в кадре это хвост Ethernet-паддинга:
  груз на этой двери 46 байт = 28 + 18 нулей, и запись видна в логе);
* `27,20` — клетка, разделяющая два события: страж говорит «да»
  (`27 >= 8`, `20 <= 20`), а `skb_ensure_writable(27+20 = 47)` на 46-байтном
  skb — «нет». Счётчик 1, сообщения в логе нет, кадр обработан как был;
* `8,21` отказано только потому, что длина 21 > 20.

Судьба у ARP-плеч — не счётчик, а **соседская таблица**, и она говорит, что
именно запись сделала:

* `a_8_6` пишет только SHA → ядро учит `10.59.0.11 → a0:a1:a2:a3:a4:a5`:
  чужая запись становится тем, что ядро запомнило;
* `a_14_4` пишет SPA (10.59.0.77) → запись появляется **у 10.59.0.77**, а у
  .11 её нет: запись в адрес отправителя выбирает, к какому адресу относится
  то, что ядро выучит;
* `a_24_4` пишет TPA (10.59.0.99) → не учится **ничего**: цель больше не мы;
* `a_8_20` пишет тело целиком, и вместе с SHA уезжают SPA (166.167.168.169) и
  TPA (176.177.178.179) — поэтому «выученного» нет вовсе;
* `a_6_2` подменяет `ar_op` на 2 (reply) → ответ на запрос не обрабатывается и
  тоже ничего не учит.

То есть у ARP-двери «принято стражем» и «повлияло на состояние стека» — разные
события, и второе видно только по таблице соседей.

## 5. Сумма: `csum type inet` — это не одно, а три разных

```
net/netfilter/nft_payload.c:1162
	if ((priv->csum_type == NFT_PAYLOAD_CSUM_INET || priv->csum_flags) && …)
		if (priv->csum_type == NFT_PAYLOAD_CSUM_INET &&
		    nft_payload_csum_write_ok(pkt, priv) &&
		    nft_payload_csum_inet(skb, src, fsum, tsum, csum_offset))
			goto err;
```

Ложное `nft_payload_csum_write_ok()` — не отказ: фиксация просто не делается,
запись делается. Что этот страж требует:

| база | семья/дверь | условие | следствие |
|---|---|---|---|
| `@nh` | `ipv4` (дверь 3), `inet` prerouting (5), `inet` ingress (1), `netdev` ingress (0) | `csum_offset == 10` | правится **сумма заголовка IPv4** |
| `@nh` | `ipv6` (дверь 2) | никогда | **молчание** |
| `@th` | любая | `tprot` = UDP и `csum_offset == 6` | правится поле, названное правилом |
| `@ll` | любая | — | отказ при загрузке (`-EINVAL`) |

### 5.1 `@nh` + `inet` в IPv4: правит сумму, которую уже никто не проверяет

`v4_sr_no` пишет адрес источника **без** фиксации, и `IpInHdrErrors` **0**:
сумма заголовка IPv4 проверяется в `ip_rcv_core()`, то есть **до**
prerouting-хука, и после записи её не смотрит никто. `v4_sr_cs` — те же байты
плюс фиксация — тоже даёт `IpInHdrErrors` 0. Разница между ними видна только в
логе (в поле суммы) и ни в чём другом: **на этой двери `csum type inet` правит
то, что уже проверено**.

`v4_ttl_cs` показывает, что механизм работает: TTL не входит в псевдозаголовок,
поэтому датаграм доставлен (сокет 1). А `v4_sr_cs` — что он не спасает: адрес
источника в псевдозаголовок входит, сумма UDP остаётся старой, `UdpInErrors` 1.

### 5.2 Та же запись на ingress-двери — совсем другой исход

| плечо | дверь | запись | IpInHdrErr | сокет |
|---|---|---|---|---|
| i1_ttl_no | `inet` ingress | `@nh,8,1 = 3f` без суммы | **1** | 0 |
| i1_ttl_cs | `inet` ingress | то же + `csum type inet, off 10` | 0 | **1** |

На ingress-двери `ip_rcv_core()` идёт **после** хука: сломанная сумма заголовка
здесь действительно убивает пакет, а фиксация действительно спасает. Одна и та
же запись, одна и та же сумма, две двери — и на одной она не нужна, а на другой
без неё нельзя.

### 5.3 `@nh` в IPv6: страж говорит «нет», и это молчание

`v6_s_cs` пишет адрес источника (`@nh,8,16`) с `csum type inet` — правило
загружается, счётчик 1, запись состоялась, сумма UDP6 осталась старой,
`Udp6InErrors` 1, сокета нет. `nft_payload_csum_nh_write_ok()` для
`NFPROTO_IPV6` возвращает `false`, и это не отказ: у IPv6 нет суммы заголовка,
которую эта ветка умеет править. Тот же смысл, выраженный **другим атрибутом**
(`csum_flags=1`, обновление псевдозаголовка), работает: `v6_s_fl` доставлен.
То есть у «поправить сумму» два написания, и на базе `@nh` в IPv6 одно из них
делает вид, что сделало.

### 5.4 `@th` и нулевая UDP-сумма: поправка **создаёт** ту, которой не было

`v4_u0_no` — кадр с `UDP checksum = 0` (законно для IPv4), запись 4 байт
полезной нагрузки без фиксации: доставлен, суммы никто не проверяет.
`v4_u0_cs` — те же 4 байта с `csum type inet, off 6`: `nft_payload_csum_inet()`
берёт из поля **ноль** и прибавляет к нему дельту, то есть записывает
**ненулевое** значение, которое не является суммой изменённой датаграммы;
получатель теперь проверяет и падает — `UdpInErrors` 1.
`v4_u0_fl` — те же байты с `csum_flags=1`: `nft_payload_l4csum_offset()`
отказывается (`if (!nft_payload_udp_checksum(...)) return -1`), фиксация
**пропускается**, поле остаётся нулём, датаграм доставлен.

Три плеча, одна дверь, один кадр, одни и те же четыре байта: «не трогать» →
доставлено, «поправить штатным флагом» → доставлено, «поправить `csum type
inet`» → убито.

### 5.5 Три отказа при загрузке, которых не видит счётчик

`v4_cs_o11` (`csum_offset` 11 на базе `@nh` в семье `ipv4`), `ll_cs`
(`csum type inet` на базе `@ll`) и `th_cs_fl` (`csum type inet` **вместе** с
`csum_flags` на `@th`) — все три `-EINVAL` при загрузке правила: правила нет,
счётчик 0, кадр идёт как шёл. Это единственные клетки хода, где «правило
существует» — неправда.

## 6. `inet` на обеих дверях: на layer-3 это `ip`, на ingress — не `netdev`

| плечо | дверь | запись | IpInHdrErr | UdpInErr | сокет |
|---|---|---|---|---|---|
| v4_sr_cs | `ipv4` prerouting | `@nh,12,4` + ct 10 | 0 | 1 | 0 |
| t4_s_cs | `inet` prerouting | то же | 0 | 1 | 0 |
| v4_sr_no | `ipv4` prerouting | `@nh,12,4` без суммы | 0 | 1 | 0 |
| t4_s_no | `inet` prerouting | то же | 0 | 1 | 0 |

На layer-3 `state->pf` — семья **пакета** (`nf_register_net_hook()` ставит одни
и те же ops в списки ipv4 и ipv6, а `nft_do_chain_inet()` разбирает по
`state->pf`), поэтому `inet`-дверь ведёт себя ровно как `ipv4`/`ipv6` — все
четыре клетки совпадают. Странная дверь — не семья `inet`, а **ingress**: там
`pf` переписывается, и обе границы (§2) становятся другими.

### 6.1 Пустая цепь `inet` на ingress — не пустая

| кадр | таблица `inet` | счётчик netdev | свидетель prerouting | Ip6In | Ip6HdrErr |
|---|---|---|---|---|---|
| F5 (hop-by-hop) | есть | 1 | 0 | **0** | 1 |
| F5 | удалена | 1 | 0 | **1** | 1 |
| F6 (destination options) | есть | 1 | 0 | **0** | 1 |
| F6 | удалена | 1 | **1** | **1** | 1 |

`nft_do_chain_inet_ingress()` вызывает `nft_set_pktinfo_ipv6_ingress()` **до**
первого правила: `ipv6_find_hdr()` обходит цепочку расширений и при неудаче
возвращает `NF_DROP` и считает `IPSTATS_MIB_INHDRERRORS`. Поэтому:

* F5 (hop-by-hop со `hdrlen 255`) умирает в `ip6_rcv_core()` **в обоих случаях**
  (`if (hdr->nexthdr == NEXTHDR_HOP)` живёт там, до хука), и разница только в
  том, кто посчитал: без таблицы `Ip6InReceives` = 1, с таблицей — 0;
* F6 (destination options) — та клетка, где разница в **свидетеле**: без таблицы
  кадр доходит до prerouting (`pnl` 1) и умирает позже, с таблицей — не доходит
  (`pnl` 0). Пустая цепь на ingress отнимает у стека кадр, который он сам
  разобрал бы позже.

## 7. Предсказания: 12 из 15 целиком, два — по одной клаузе, одно опровергнуто

Сошлись целиком P1, P2, P3, P4, P5, P8, P9, P10, P11, P12, P14, P15.
Частично P6 и P13. Опровергнуто целиком P7.

**P6 опровергнуто в главной клаузе и уточнено:** запись `8,20` на ARP-двери
пишет не только SHA — вместе с ним уезжают SPA и TPA, поэтому «ядро выучит
`a0:a1…`» неверно: оно не выучит ничего. Клауза измерена заново клеткой `8,6`
(только SHA), где это видно; вторая клауза (SPA) и третья (TPA) сошлись.

**P7 опровергнуто:** «`csum type inet` на `@nh` в IPv4 делает датаграм
доставленным» — нет. Сумма заголовка правится (и это видно: `IpInHdrErrors` 0),
но сумма UDP покрывает адрес источника, поэтому `v4_sr_cs` умирает с
`UdpInErrors` 1, как и `v4_sr_no`. Механизм подтвердился, следствие — нет; и
заодно выяснилось, что на prerouting-двери эта сумма уже никому не нужна
(§5.1), а нужна она на ingress (§5.2).

**P12 сошлось числом, но моя формулировка была неточной:** я ждал, что `inet`
на prerouting совпадёт с `ip` — совпало, но не потому, что «inet особый», а
потому, что там `state->pf` — семья пакета; особый случай — ingress.

**P13 опровергнуто во второй клаузе:** «без таблицы кадр дойдёт до prerouting»
верно только для F6; F5 умирает в `ip6_rcv_core()` в обоих случаях, потому что
hop-by-hop разбирается там, а не в `ip6_input()`. Клетка F6 добавлена именно
затем, чтобы вторая клауза стала измеримой.

## 8. Ошибки хода, все мои

1. **`be32_out()` с `htonl()`** — в сборщиках кадров F2/F3/F4 адреса IPv4
   уехали в обратный порядок байт: кадры адресовались 1.0.59.10, а не
   10.59.0.1. Весь IPv4-раздел первого дыма мерил `IpInAddrErrors` вместо
   доставок; поймал по `FRMPY` (адрес на проводе `0b003b0a`), а не по
   счётчику.
2. **Недописанная длина в F5** — `payload_len` был равен длине UDP-датаграммы
   (34), а не восьми байтам заголовка расширения; кадр умирал в проверке
   `pkt_len + 40 > skb->len` (`Ip6InTruncatedPkts` 1), и раздел `BAD` мерил не
   ту смерть. Второй дым; после починки появилась строка F6.
3. **Немедленное значение — это `struct nft_data`, 16 байт.** Запись длиной 20
   и 21 байт заряжалась одним `immediate` и получала `-EOVERFLOW` (`-75`),
   которого я не ждал: F58 это уже измерил на 32 байтах, я не перенёс. Лечил
   двумя иммедиатами в `REG32_00` и `REG32_04` и одной записью из регистра.
4. **Соседская таблица текла между плечами**: перед ARP-плечом я удалял
   только запись 10.59.0.11, а `a_14_4` научил .77 — и в `a_24_4` «выученное»
   было чужим. Теперь удаляются все три адреса, которые может создать прибор.
5. **Модель верификатора была неверна трижды, все три — в первом дыме:**
   плечи-переписи печатают сообщение в лог (у них нет записи, но `log` в
   правиле есть), `indev`/`pindev` печатаются как `«индекс:имя»`, и — самое
   полезное — путь `csum_flags` **не использует** `csum_offset` правила, а
   находит смещение суммы транспорта сам (`nft_payload_l4csum_offset()`), так
   что моя модель писала поправку в начало заголовка IPv6.
6. **Селфтест нашёл две настоящие дыры в верификаторе:** длина доставленной
   датаграммы (`u6l`/`u4l`) не проверялась вовсе, а печатные параметры плеча
   (`off`, `door`, `base`, …) не сверялись с таблицей в исходнике прибора —
   то есть порча самого поля в логе проходила. Обе добавлены, после чего
   выживших мутаций не осталось.

## 10. Что не измерено, прямо

* **Настоящего устройства с `CHECKSUM_PARTIAL` нет.** Условие
  `skb->ip_summed != CHECKSUM_PARTIAL` в `nft_payload_set_eval()` — это ветка,
  в которой поправка `@th` **не делается** (железо посчитает само). Все кадры
  здесь вброшены через `AF_PACKET`, то есть `CHECKSUM_NONE`; проверка требует
  датаграммы из сокета через `veth` (второй netns), и это следующий замер.
* `@th` с `csum type inet` для **TCP** (`csum_offset` 16) и ICMP (2);
  `NFT_PAYLOAD_CSUM_SCTP`; `csum_flags` на базе `@nh` в IPv4 (обновление суммы
  L4 при записи адреса).
* `@nh` с `csum` на **netdev**-двери (ветка `pkt->skb->protocol == ETH_P_IP`
  в `nft_payload_csum_nh_write_ok()`) — здесь она не тронута.
* IPv4 с **опциями** (`ihl > 5`): список разрешает запись по смещениям до 16
  включительно, а при `ihl = 15` сумма заголовка лежит на 10, но заголовок
  длиной 60 байт списком не покрыт вовсе.
* Фрагменты (`fragoff != 0`) для `@th`; GSO; `br_netfilter`; семья `bridge`
  для `@nh` (её ветку мерил F31, здесь — нет); QinQ и PPPoE на этих дверях.
* **Не уязвимость**: все правила ставил root в начальном user ns — по F57
  запись в пакет вообще возможна только там.
