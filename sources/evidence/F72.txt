F72 -- what a user page does to the two UDP GRO doors, measured at the doors

Kernel 7.3.4-T563 (`1efbc957…2033`), no new build. Same three-netns IPv4 path as before, with
three additions: the sender can set SO_ZEROCOPY and pass MSG_ZEROCOPY, the
receiver can open a packet socket on its device that either keeps every frame
or carries a `ret 0` filter so it keeps none, and the forward chain finally
carries a `log` rule, so "what the rule saw" is a number rather than an
inference. Thirteen arms, two attempts each, two boots, all 52 identical in
every modelled field.

1. skb_gro_receive() refuses a zerocopy datagram outright
   (net/core/gro.c:112: `if (skb_zcopy(p) || skb_zcopy(skb)) return
   -ETOOMANYREFS;`). Six 512-byte datagrams sent with MSG_ZEROCOPY through
   rx-udp-gro-forwarding reach the forwarding hook as SIX packets, each with
   the UDP length field 520. The same six copied datagrams reach it as ONE
   packet with the length field 3080. skb_gro_receive_list() -- the
   rx-gro-list door -- has no such check and merges the same zerocopy burst
   into one packet of 3080. The sender's memory, not the socket, decides.

2. The receiving queue is where zerocopy costs the most. Every enqueue record
   satisfies ts = end + 576 + PAGE_ALIGN(data_len) for a zerocopy skb and
   ts = end + 576 otherwise: 5056 for a 512-byte payload, 5056 for 1200, 9152
   for 5000, against 1280 for a copied 512-byte datagram. The charge is one
   page per payload, not one page per page touched -- a payload deliberately
   placed across a page boundary is charged the same 4096. With
   SO_RCVBUF 19200 (sk_rcvbuf 38400) a 64-datagram zerocopy burst leaves 7
   datagrams and 57 drops, where a copied burst would leave 30.

3. The copy happens in the receiver and only one door pays it per datagram.
   ip_local_deliver_finish() calls skb_orphan_frags_rx() ->
   skb_copy_ubufs() for anything with SKBFL_ZEROCOPY_ENABLE. Counted on the
   function: six copies for six datagrams on the linear door, and ONE for the
   fraglist aggregate -- because the aggregate IS its first member, so that
   member's payload is copied and its flag cleared while the five frag_list
   members keep the sender's pages all the way to the receiving socket.

4. SKBFL_PURE_ZEROCOPY -- the only thing that makes skb_frags_readable()
   false, and therefore the third clause of skb_condense()'s early return --
   is written in exactly one place in this tree (net/ipv4/tcp.c:1331). A UDP
   skb cannot carry it; the copy in (3) is the proof that the predicate was
   true, since skb_copy_ubufs() returns -EFAULT for a PURE skb and the caller
   drops the packet.

5. skb_cloned() is a predicate about liveness, not a bit. With the two
   datagrams 512+148 merged into one 668-byte packet and delivered whole:
   no second consumer -> one __pskb_pull_tail of 148 bytes, charge 1280;
   an egress AF_PACKET tap -> no pull, charge 2240; an ingress AF_PACKET tap
   -> the same, through skb_share_check() in ip_rcv_core() instead of
   dev_queue_xmit_nit(); and a packet_type with a `ret 0` filter, which never
   keeps a frame -> no clone at all, the bit is 0, the pull happens and the
   charge is 1280. The last case is the interesting one: merely registering a
   second consumer changes nothing, because __netif_receive_skb_core() calls
   the last packet_type without taking a reference.

Nothing here is a vulnerability: every rule was installed by root in the
initial user namespace, and creating a kprobe needs CAP_SYS_ADMIN.


===== SUMMARY.md =====
# F72 — a zerocopy sender, two doors, and the three ways into `skb_condense()`'s early return

Turn 594. Kernel `7.3.4-T563` (`1efbc957…2033`), **no new build**. Instrument
`differ594`, modes `zc`/`cl` — **13 arms × 2 attempts × 2 boots = 52 measured
attempts**. Predictions frozen before the first boot (`research/predictions_594.md`).

The two debts, in F71 §8's own words:

> **Клауза 3** (`!skb_frags_readable`) не срабатывает и от «прошла» здесь
> неотличима: skb с `SKBFL_PURE_ZEROCOPY` в этой топологии нет.

and the standing intention *«кто ещё на приёмном пути ставит `skb_cloned` … и
достижима ли клауза 2 без наблюдателя»*.

Both are answered — one by a reachability argument backed by a measurement of
the copy that *does* happen, one by a ladder of four arms in which the
predicate, not the bit, decides. And the zerocopy sender itself turned out to
be a much richer instrument than expected: it splits the two GRO doors apart
and it makes the receive queue charge **four times more**, not less.

## 0. What the source says, and what the arms are built from

Four readings decide the arms (`research/predictions_594.md` §1, frozen
before the first boot):

1. **`skb_gro_receive()`** (`net/core/gro.c:112`) refuses, before anything else,
   `if (skb_zcopy(p) || skb_zcopy(skb)) return -ETOOMANYREFS;` — the **linear**
   door (`rx-udp-gro-forwarding`) cannot merge a datagram whose payload lives in
   user pages. **`skb_gro_receive_list()`** (the **fraglist** door,
   `rx-gro-list`) has no such check.
2. **`SKBFL_PURE_ZEROCOPY` is set in exactly one place** in this tree,
   `net/ipv4/tcp.c:1331`, and cleared at `tcp.c:1020`. UDP's `ip_append_data()`
   sets `SKBFL_ZEROCOPY_FRAG` (`ZEROCOPY_ENABLE|SHARED_FRAG`), never the PURE
   bit, so a UDP datagram cannot make `skb_frags_readable()` false.
3. **`ip_local_deliver_finish()`** (`net/ipv4/ip_input.c:231`) calls
   `skb_orphan_frags_rx()` → `skb_copy_ubufs()` for anything carrying
   `SKBFL_ZEROCOPY_ENABLE`: the payload is copied into kernel pages **in the
   receiving host**, before `udp_rcv()`.
4. **`skb_gro_receive_list()`** ORs only `SKBFL_SHARED_FRAG` into the
   aggregate, and the aggregate **is** its first member — so the head's own
   payload is copied and its zerocopy flag cleared, while the frag_list
   members keep their user pages.

New in the instrument (F71's three-netns IPv4 path unchanged): the **sender**
can use `SO_ZEROCOPY` + `MSG_ZEROCOPY`, the **receiver** can open a packet
socket on y3 that either keeps every frame or carries a `ret 0` filter so it
keeps none, and the forward chain — **empty since F68** — finally carries a
`log` rule, so "what the rule saw" is a number (NFLOG packet count and every
UDP length field) instead of an inference.

Probes (8): `skb_condense`, `__udp_enqueue_schedule_skb` (the gate),
`__pskb_pull_tail`, `skb_segment_list`, `___pskb_trim`, `skb_clone`,
`pskb_expand_head`, and new in this turn **`skb_copy_ubufs`** — the copy
itself.

## 1. The two doors disagree about zerocopy, in one table

Six datagrams of 512 bytes, one burst, same socket, same route; only the
sender's memory and one device bit change:

| arm | sender | door | packets at the rule | `uh->len` | gate | charge |
|---|---|---|---|---|---|---|
| `z_ctl6` | copy | linear | **1** | 3080 | 6 enq, `dlen` 0 | 7680 |
| `z_lin6` | MSG_ZEROCOPY | linear | **6** | 520 each | 6 enq, `dlen` **512** | **30336** |
| `z_fl6` | MSG_ZEROCOPY | fraglist | **1** | 3080 | 6 enq, `dlen` 512 | **55616** |

The linear door merges *nothing*: every zerocopy datagram flushes the flow
(`skb_zcopy()` → `-ETOOMANYREFS`), so six datagrams reach the rule as six
packets while the same six copied datagrams reach it as one packet of 3080
bytes. The fraglist door has no such check and merges them. Same datagrams,
same door bit that F65–F71 used for a different question, opposite answer —
and the reason is a property of **the sender's memory**, which no socket
option exposes.

`z_ctl6` also refutes half of P1: on a *plain* socket the aggregate is
segmented by `skb_segment()` before the queue, so the gate sees six records
with `dlen` 0 and `ts` 1280, not one record with `dlen` 2560 (F71 saw that
shape only on the UDP_GRO socket).

## 2. A zerocopy datagram costs the receive queue a whole page — four times a plain one

Every enqueue record satisfies one identity:

```
ts = end + 576 + (PAGE_ALIGN(dlen) if the skb is zerocopy else 0)
```

| arm | payload | gate record | `ts` |
|---|---|---|---|
| `z_lin1` | 512 | `dlen` 512, `end` 384 | **5056** = 384+576+4096 |
| `z_lin1q` | 1200 | `dlen` 1200, `end` 384 | **5056** |
| `z_lin1w` | 5000 | `dlen` 5000, `end` 384 | **9152** = 384+576+8192 |
| `c_none` (plain) | 512 + 148 | `dlen` 148, `end` 704 | 2240 (sum: 1280 + 960) |

Zero-copy is not cheaper for the receiver — it is **3.95× more expensive per
512-byte datagram** (5056 against 1280), and the charge is one page per
*payload*, not one page per page the payload touches: `z_lin6x`, whose payload
starts at offset 3600 and therefore straddles a page boundary, still charges
4096. Three payload sizes and three buffer alignments, one formula.

The consequence is a budget, not a footnote: with `SO_RCVBUF 19200` →
`sk_rcvbuf 38400`, 64 zerocopy datagrams leave **7** in the queue
(`7 × 5056 = 35392 ≤ 38400 < 8 × 5056`) and 57 errors; the same buffer holds
**30** plain 512-byte datagrams (P10 predicted “more than 30”).

## 3. The copy happens in the receiver, and only one door pays it per datagram

`skb_copy_ubufs()` counted per arm:

| arm | copies | where the payload ends up |
|---|---|---|
| `z_lin6` | **6** | all six copied in the receiving host, none left zerocopy |
| `z_fl6` | **1** | only the aggregate's own head is copied; five members keep the sender's pages to the socket |
| `z_lin1`/`z_lin1q`/`z_lin1w` | **1** | the single datagram copied |
| `c_*` (no zerocopy) | 0 | — |

So the fraglist door is not “worse” or “better”: it delivers the same six
datagrams with **five of them still pointing at the sender's memory**, at the
price of a 55616-byte queue charge instead of 30336 — and the aggregate record
`30336` is exactly `6 × 5056`, because `skb_gro_receive_list()` does
`p->truesize += skb->truesize` for every member.

## 4. Clause 3: a TCP flag on a UDP-only queue, and the copy proves it

`SKBFL_PURE_ZEROCOPY` is written in one place in this tree and read by
`skb_frags_readable()`, which is the third clause of the early return. A UDP
zerocopy skb carries `ZEROCOPY_ENABLE|SHARED_FRAG` and never the PURE bit, so
clause 3 cannot fire for UDP at all. This is not only a reading: `skb_copy_ubufs()`
returns `-EFAULT` when `!skb_frags_readable()` (`net/core/skbuff.c`), and
`ip_local_deliver_finish()` *drops the packet* on that error. The 6 and 1
copies above are the measurement that the predicate was true — the payloads
were copied, not discarded.

## 5. Clause 2: the bit is not the predicate, and an observer that keeps nothing leaves nothing

Four arms, the same two datagrams (512 + 148) merged at x0 into one packet of
668 bytes, delivered whole to the UDP_GRO socket:

| arm | second consumer | `fl` bit 0 | `__pskb_pull_tail` | charge |
|---|---|---|---|---|
| `c_none` | none | 0 | 1 (`eat` 148) | **1280** |
| `c_egr` | egress tap on y1 (`dev_queue_xmit_nit`) | 1 | 0 | **2240** |
| `c_ing_k` | **ingress** tap on y3 (`skb_share_check` in `ip_rcv_core`) | 1 | 0 | **2240** |
| `c_ing_d` | ingress packet_type with a `ret 0` filter (keeps nothing) | **0** | 1 | **1280** |

Two different code sites set the bit and both fire the clause, so *which*
observer does not matter. What matters is whether the second reference to the
same data is **alive at the gate**: a packet_type that drops its copy leaves
no trace at all — not even the bit, because `__netif_receive_skb_core()` calls
the *last* packet_type without taking a reference, so `skb_share_check()` sees
`users == 1` and never clones. P14 had the bit at 1 here; it is 0.

So the answer to “is clause 2 reachable without an observer” is: on this path,
no. Every mechanism that shares the head is a packet socket, a mirror or a
topology feature that does not survive forwarding — and the forwarder itself
defends against a clone that does reach it (`ip_forward()` copies before
decrementing the TTL, `skb_cow()` → `pskb_expand_head()`).

## 6. What `head_frag = 1` would need — a source answer, not a measurement

The `else if (skb->head_frag)` branch of `skb_gro_receive()` moves the
incoming skb's linear head into a page frag of the aggregate. It never fires
in this stand and cannot: the only writers of `head_frag = 1` in this tree are
`build_skb()`, `build_skb_around()`, `napi_build_skb()` and `napi_alloc_skb()`
(`net/core/skbuff.c:513,535,581,815` are the four `skb->head_frag = 1` lines
plus `napi_alloc_skb`'s own at 885), and every caller is a device driver,
`net/core/xdp.c`, or `napi_get_frags()`. veth forwards skbs unchanged, vxlan
reuses the outer skb, and TUN — the only virtual driver that would use
`napi_get_frags()` — is not in this kernel's config. F71 measured the bit at
the door (byte 126, bit 5) as 0 in all 66 records; this turn's 52 attempts show
it in no record either. The branch stays a named debt with a source answer
attached, not a cell.

The four refutations are all one misunderstanding: I assumed a zerocopy skb is
*cheaper* for the receiver and that the aggregate would keep its members'
zerocopy state. It is the opposite on both counts, and the mechanism
(`PAGE_ALIGN` per payload, and the head being a member) is now measured.

## 8. Errors of the run, all mine

1. **The `'d'` command was 8 bytes while the sender reads 16** — the command
   stream desynchronised after the first arm of smoke A; its odd numbers (the
   5056/9152 alternation, empty second attempts) came from scrambled
   parameters, not from the kernel. Smoke A is discarded; `z_lin6x` was built
   to *test* the alternation theory and did not reproduce it.
2. **The `c_*` arms were first built on a plain socket**, where the aggregate
   is segmented before the queue; the gate then never sees `data_len > 0`.
   Switched to the UDP_GRO socket — F71's own cell — before the measured boots.
3. **The forward chain had been empty since F68**: no rule, no NFLOG, so the
   first two smokes had no witness at the rule at all. A `log`+`count`+`accept`
   rule was installed and the two later smokes show `n=1` vs `n=6`.
4. **My `exp_*` columns in the arm table were wrong** for several arms
   (`z_ctl6`: `exp_enq` 1 while six are enqueued; `exp_cond` 6 while
   `skb_condense()` only runs above half a buffer). The table is frozen; the
   verifier does not use those columns, and the disagreements are listed here.
5. **The verifier crashed twice instead of going red** (`KeyError` on the
   attempt loop after the arm count changed) — found by running, not by a
   selftest, because the selftest did not exist yet. It now turns any crash
   into a red count with exit 2.
6. **`z_lin1w` reads 4096 bytes of a 5000-byte datagram**: the receiver's
   buffer is 4 KiB, so `dl0=4096` is the witness truncating, not the kernel
   trimming. The gate record (`dlen` 5000, `ts` 9152) is unaffected; the
   delivered length in that arm must not be quoted.
7. **`clone=5` in `z_ctl6`** is not modelled: five `skb_clone()` calls in an
   arm with no packet socket, with `skb_segment_list` never called — the
   aggregate is split by `skb_segment()`, and something in that path clones.
   Measured, not explained.

## 9. What is not measured, stated plainly

The exact site of the `PAGE_ALIGN` charge: the only such line in the copy path
is `zerocopy_fill_skb_from_iter()`'s `skb->truesize += PAGE_ALIGN(copied + start)`,
and with `start` = the payload's offset in its page it would predict 8192 for
`z_lin6x` (offset 3600); measured 4096 at three offsets. Either that `start` is
not the buffer's page offset or another site charges the page — **not
established**. Also: the five clones of `z_ctl6`; `cond=3` in the 64-datagram
arm (three condense calls above half a buffer, not modelled); IPv6 (all of F72
is IPv4); TCP (where PURE_ZEROCOPY actually lives); tunnels;
`CHECKSUM_COMPLETE`; a real NIC. **Not a vulnerability**: every rule was
installed by root in the initial user namespace and creating a kprobe requires
`CAP_SYS_ADMIN` (F57).
