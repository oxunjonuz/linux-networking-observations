Theme: `meta protocol` on a PPPoE frame computes one number and two bases read
it differently -- and at an egress door the difference decides whether the frame
is refused or rewritten in its real transport header.

No diff below: this measures the guard as it stands and proposes no change.

Linux 7.3.4, nftables in the initial user namespace, one packet at a time, one
rule at a time.  The frame is built by the kernel: a PF_PPPOX session socket
(sid 99) bound to a veth, `send()` hands it `00 57` + IPv6/UDP, `pppoe_sendmsg()`
adds the session header and the Ethernet header.  On the wire the IPv6 header is
at offset 22 and `skb_network_offset` is 14, because `skb_reset_network_header()`
runs before `dev_hard_header()`.

`nft_meta_pktinfo_may_update()` computes `nhoff = 8 + skb_network_offset` = 22.
`__nft_set_pktinfo_ipv6_validate()` then reads the version byte at
`skb_network_offset + nhoff` = 36 (which is `saddr[6]`) while
`ipv6_find_hdr()` starts the walk at `nhoff` = 22 (the real header).  The same
expression therefore gives the transport base the right answer and the network
base the wrong one; and when the version check fails,
`nft_set_pktinfo_unspec()` resets `nhoff` to 0, so `@nh` silently falls back to
the PPPoE header.

Measured on that door (25 arms x 2 boots):

  - `meta protocol` reports `0x86dd` and `meta l4proto` reports nothing;
  - `@nh,7,1` and `@th,0,2` are both refused, for two different reasons
    (`nft_nh_write_ok_netdev()` has no `ETH_P_PPP_SES` case; `pkt->flags` is 0);
  - with `0x60` at offset 36 in the frame's own source address the version
    check passes, and the same `@th,0,2` write lands at offset 62 -- the real
    UDP source port -- while `@nh,0,4` reads the attacker's four bytes at 36;
  - at the ingress hook of the same device, with the same bytes, `@nh,7,1` is
    accepted (the guard is a constant there) and lands in the PPP protocol
    field.

The same instrument closes the transport base for plain IPv6: `@th,0,2` lands
at `14 + 40` at local_out, postrouting and the netdev egress hook, the local
class is delivered with the written source port, the forwarded class dies on the
UDPv6 checksum until `csum type inet` (`csum_offset 6`) is added, and
`meta l4proto` reports 51 for AH (the walk stops on the auth header) and 17
through a routing header.

Not a vulnerability: the rules are installed by root in the initial user
namespace.  The report is about a guard whose coordinate depends on the hook and
about a validation that looks at one place while the walk parses another.

# F48 - IPv6 inside PPPoE at an egress door, and @th where the walk meets the doors

Kernel `7.3.4-T563` (`1efbc957...2033`), the image of F41-F47; no new build.
Turn 570.  Two debts, both named at the end of 569.

## 1. Debt 1: `meta protocol` gives the same number to two bases, and one of them
##    reads it twice

`nft_meta_pktinfo_may_update()` on an `ETH_P_PPP_SES` frame computes
`nhoff = PPPOE_SES_HLEN + skb_network_offset(skb)` = `8 + noff`.  Inside
`__nft_set_pktinfo_ipv6_validate()` that one number is used in two places:

```
ip6h  = skb_header_pointer(skb, skb_network_offset + nhoff, ...)   /* version check */
thoff = nhoff;  ipv6_find_hdr(skb, &thoff, ...)                    /* the walk        */
```

On **ingress** `skb_network_offset` is 0 (`eth_type_trans` pulled the Ethernet
header), so the version check reads the real IPv6 header at 8 and the walk
starts at 8: both right.  On **egress** the skb is the one `pppoe_sendmsg()`
built -- `skb_reset_network_header()` after the PPPoE push, then 14 bytes of
Ethernet -- so `skb_network_offset = 14`, the version check reads
`14 + 22 = 36`, and the walk still starts at 22.  The same expression, the same
number, two different answers.

The writes never add `nhoff` at all (`nft_payload_set_eval` uses
`skb_network_offset + off`), so on this frame they land 8 bytes early, in the
PPPoE session header -- the F41 coordinate, now on the transmit side.

Four measured statements, each a row of that table:

* **`meta protocol` reports the inner protocol and loses the coordinate.**
  `proto_ppp` matches `0x86dd` (`nf_flow_pppoe_proto()` reads the PPP field
  through the MAC header), but validation fails at 36 and
  `nft_set_pktinfo_unspec()` resets `nhoff` to 0: `nh_m_ppp` compares `@nh,0,4`
  with `06 07 08 09` and does not match, because the read landed at 14, the
  PPPoE header.  `l4_ppp` does not match 17 at all.
* **Both writes are refused, and for two different reasons.**  `nhw_ppp`:
  `nft_nh_write_ok_netdev()` switches on `skb->protocol` and has no
  `ETH_P_PPP_SES` case.  `thw_ppp`: `pkt->flags` is 0 after `unspec`.  The wire
  is unchanged in both (`tap[54:56] = 18 19`, `tap[62:64] = 9c 40`).
* **The refusal is a property of one byte in the sender's own address.**  The
  crafted frame carries `0x60` at 36 (`saddr[6]`) and a payload length at 38;
  validation passes, the walk still starts at 22, so `fak_l4` reports 17,
  `fak_nh` reads `60 00 00 08` -- the attacker's bytes -- at 36, and `fak_thw`
  writes `9091` at 62: **the real transport header** (`tap[62:64] = 90 91`).
  One rule, one cell, one frame; the difference between refused and landed is
  four bytes of the source address.
* **Ingress accepts what egress refuses.**  `in_nhw` writes at `data + 7`, the
  PPP protocol field (`s[6:8] = 00 90`), because at `NF_NETDEV_INGRESS`
  `nft_nh_write_ok()` returns a constant true.  `in_thw_m` writes at
  `data + 48`, the real sport, once `meta protocol` has set the flags.  Without
  it (`in_thw`, `in_rdth`) the transport base is refused at ingress too.

And one measurement about the instrument itself: on the receive path the
AF_PACKET copy is the frame **before** the rule wrote it (`in_nhw`:
`s[6:8] = 00 90`, `tap[21] = 57`), while on the transmit path it is the frame
after (`fak_thw`: both 90 91).  A tap is not a witness of what a rule did on
ingress; the NFLOG payload at the same rule is.

* **The base is right everywhere.**  `thw` on the local class lands at frame
  54 = `14 + 40` at all three doors (the egress door sees
  `skb_network_offset = 14` and `thoff = 54`; the layer-3 doors see 0 and 40),
  and the receiver reports the written source port `37009`.  On the forwarded
  class the same write at the same byte breaks the UDPv6 checksum
  (`u6err = 1`, no delivery) and `csum type inet` with `csum_offset 6` repairs
  it: delivered, `u6sport = 37009`.  Nothing in this base depends on the door.
* **The walk's two named exceptions are measured.**  `meta l4proto` reports 17
  through a hop-by-hop, through hop-by-hop + dest-opts and **through a routing
  header** (segments_left 0, `IP6_FH_F_SKIP_RH` not set), and **51** for the AH
  shape: `IP6_FH_F_AUTH` stops the walk on the authentication header, so the
  transport base points at the AH header and nothing after it is reachable.
  With `csum inet` the three non-AH shapes deliver to the written sport
  (`u6sport = 37009`) -- the receiver names the coordinate without a tap --
  and the AH shape delivers nothing either way.
* **What is not measured here:** the child's packet socket did not capture the
  three extension shapes (`tapn = 0`); their write position is proven by the
  receiver's source port, not by a wire hexdump.

## 4. Errors of the turn, all mine

1. `A6_P_FS` put `0x60` at `saddr[8]` instead of `saddr[6]`; the crafted frame
   was crafted at the wrong byte and all three `fak_*` arms read 0.  Found by
   reading the first smoke against the model, before any number reached a
   document.
2. The plain control datagram carried the base helper's payload while the tap
   needle looked for mine, so every `*_plain` arm had `tapn = 0` and I read it
   as "no frame on the wire".
3. `in_rdth` inherited `meta_proto = 1` from the arm before it and measured the
   same thing twice.
4. The `cs` arms used `csum type 6` from the prose of 565; the uapi value is
   `NFT_PAYLOAD_CSUM_INET = 1`, and 6 returned `-EOPNOTSUPP` on every one of
   them in the first smoke.
5. The verifier's first three versions: the walk returned the IPv6 header
   offset instead of the transport offset; `ipv6_find_hdr()` with `*offset = 0`
   starts at `skb_network_offset`, not at 0; the guard reads `skb->protocol`,
   not the inner ethertype.  Each was a red battery on correct data.
6. Two smokes ran at once (a `nohup` that "failed" had started), and their two
   boots interleaved into one log; the arms looked randomly duplicated.
7. `f570_selftest` caught two real holes in the verifier (`u6sport` was never
   checked on the local class; the printed `F570 FRAME` line was not compared
   with the frame at the door) and one crash (`MUT_tapbyte`).

user namespace.  The consequences measured are: a write that lands eight bytes
early in the PPPoE session header on the transmit side, a read base that doubles
`skb_network_offset` inside one expression, a frame whose refusal depends on the
sender's own address bytes, and a transport base that is reachable on ingress
and not on egress for the same bytes.
