Theme: the PPPoE store lands eight bytes before the field it names, and in the
IPv6 branch one cell rewrites the PPP protocol.

No diff below: the offsets it reports are the ones the guard already uses.

Three measurements on Linux 7.3.4, nftables in the bridge prerouting hook,
one rule at a time, one PPPoE session frame at a time.  The frame is a real
one: eth | 0x8864 | PPPoE session (sid 99) | 0x0021 | IPv4/UDP, and the
receiving side is a real PPP unit (`/dev/ppp`: PPPIOCNEWUNIT + PPPIOCATTCHAN +
PPPIOCCONNECT with a PPPoX socket moved to PPPOX_BOUND by PPPIOCGCHAN -- the
pppd sequence, without pppd), a real UDP socket bound on the peer address, and
the kernel's own counters.

1. `meta protocol` repairs the READ and not the STORE.

nft_meta.c, PPPoE branch: `nhoff = PPPOE_SES_HLEN + skb_network_offset(skb)`,
i.e. pkt->nhoff = 8 + 14.  nft_payload_eval() reads at
`skb_network_offset + pkt->nhoff + offset`; nft_payload_set_eval() stores at
`skb_network_offset + offset`.  The two are eight bytes apart, and the whole
`(offset,len)` white list of nft_nh_write_ok_ip4() is written in the
coordinates of the field NAME, not of the byte actually written.

Measured, with the payload `10.1.0.1 -> 10.9.0.7:5000`, 18 bytes of 0x77:

  (4,2) "ip id" = 0x0004      -> the PPPoE length becomes 4; ppp0 hands the
                                 IP stack 2 bytes; ip_rcv counts them and
                                 refuses them (InHdrErrors 1)
  (4,2) "ip id" = 0x9091      -> skb->len < length: pppoe_rcv drops the frame
                                 before the socket (0 bytes reach the stack,
                                 the counter still shows the rule ran)
  (0,2) "ver/ihl", (1,1) "tos"-> the PPPoE version/code bytes; the datagram is
                                 delivered intact
  (8,1) "ttl" = 0x45          -> the byte it writes is already 0x45: delivered
  (8,1) "ttl" = 0x90, (8,2), (10,2) "check", (12,4) "saddr", (16,4) "daddr"
                              -> all land inside the bytes covered by the IPv4
                                 header checksum; ip_rcv reports InHdrErrors
                                 and delivers nothing.  The guard never checks
                                 the checksum; the receiver always does.
  (20,4) the real saddr, (24,4) the real daddr, (6,2) the PPP protocol field
                              -> refused by the white list.  The five refused
                                 cells leave the frame byte-identical to the
                                 control: a refusal is not a drop.

2. `@ll` is bounded by 14 and that boundary is the Ethernet header, not the
   link header of the frame.

  @ll,6,2  allowed (8 <= 14) and it writes the SOURCE MAC.  pppoe_rcv() finds
           the session with __get_item(pn, ph->sid, eth_hdr(skb)->h_source,
           dev->ifindex), so the frame is then dropped: nothing reaches ppp0.
  @ll,13,1 allowed, writes the ethertype's low byte (0x8864 -> 0x88ff).  The
           frame is still delivered -- because the dispatch uses the
           skb->protocol that eth_type_trans() cached BEFORE the hook.  The
           same bytes sent from outside with no rule at all are not PPPoE and
           are not delivered.  The write is visible on the wire and invisible
           to the dispatch.
  @ll,14,2 refused (16 > 14): the PPPoE header is outside the "link header".

3. In the IPv6 branch one cell of the white list changes the PATH of the frame.

  nft_nh_write_ok_ip6() allows offset 7 with len 1 -- offsetof(ipv6hdr,
  hop_limit).  On a PPPoE frame the store is at 14 + 7 = 21, which is the low
  byte of the two-byte PPP protocol field.  With an IPv6 datagram
  (PPP protocol 0x0057) the cell writes 0x90, the protocol becomes 0x0090,
  proto_to_npindex() returns -EINVAL, and ppp_receive_nonmp_frame() queues the
  frame for pppd instead of handing it to the IPv6 stack.  What the kernel
  reports: the unit file yields the whole 68-byte frame, ppp0's
  /proc/net/dev counts 66 bytes received, and Ip6InReceives stays 0.  The
  device says "received", the stack says "nothing".

  The rest of the IPv6 list lands elsewhere too: (0,4) and (2,2) reach the
  PPPoE version/code and the SESSION ID (after which the session lookup fails
  and the frame is dropped); (8,16) -- the cell named saddr -- reaches the
  first 16 bytes of the IPv6 header (version, payload length, next header, hop
  limit, and the first 8 saddr bytes), so the same value is harmless and
  0x90... gives version 9 and Ip6InHdrErrors; (24,16) reaches saddr[8..15] and
  daddr[0..7], after which the destination is no longer local.  IPv6 has no
  header checksum, so nothing here is caught by a checksum: the version check
  and the routing table are the only things standing in the way, and one cell
  (7,1) gets past both by choosing a different protocol number.

4. For completeness: the same ARP frame, vid 100, with and without a VLAN
   device on the bridge.  Without it, the frame is PACKET_OTHERHOST and the
   arp family counter stays 0.  With `v1` (vlan 100 on br0) vlan_do_receive()
   returns true, the frame reaches arp_rcv() through v1 (counter 1), the kernel
   replies with 42 bytes and /proc/net/arp names v1 as the interface.  (8,2)
   on a single-tagged frame does not shift (the tag is already in the skb
   metadata) and really writes sha: the reply goes to the written MAC.

None of this is a privilege boundary: the rule is installed by root in the
initial user namespace.  What is worth a maintainer's look is the shape:
nft_nh_write_ok() is presented as a per-family white list of fields, but the
store is expressed in skb coordinates that do not match the coordinates the
list is written in, and the mismatch is the protocol header length.  The
IPv6 branch has a cell that reaches into another header entirely.

disk; every number above is a cell of a table that was generated from the log
and checked back against it.

# F42 — приёмная сторона PPPoE: кадр становится настоящим пакетом, и поле, которое решает путь, лежит ровно там, куда достаёт одна клетка списка IPv6

нормировки на MAC моста, который ядро выбирает заново при каждой загрузке).

## 1. Ответ в один абзац

В 563-м я записал: «приёмную сторону PPPoE я тронул только в очереди
сокета; в состоянии `PPPOX_BOUND` кадр уходит в `ppp_input()` и создаёт
`pppN` — это первый путь, где запись из моста доходит до IP-стека настоящим
пакетом». Это измерено: с настоящим юнитом (`/dev/ppp`: `PPPIOCNEWUNIT` +
`PPPIOCATTCHAN` + `PPPIOCCONNECT`, без pppd и без переговоров) датаграм из
моста приходит **в сокет на `10.9.0.7:5000` восемнадцатью байтами** своего
содержимого. И тут же выяснилось, что принимающий стек **отбрасывает все
записи, которые страж разрешает**: `meta protocol` чинит `nhoff = 8` только
для чтения, а запись по-прежнему идёт от `skb_network_offset()` — на
**восемь байт раньше** настоящего заголовка IPv4, — и каждая разрешённая
клетка ложится в поле, которое покрыто контрольной суммой заголовка.
Проверку суммы делает стек, страж её не делает никогда: пять клеток
(`ttl`, `ttl2`, `csum`, `saddr`, `daddr`) кончаются `IpInHdrErrors = 1` и
нулём доставок, а две клетки, чьё имя обещает то же самое
(`(0,2)` «ver/ihl» и `(1,1)` «tos»), попадают в **заголовок PPPoE-сессии** и
датаграм доходит целой. Второе: **отказ стража — не отбрасывание**. Пять
плеч, где запись запрещена (`bare`, `trsaddr`, `trdaddr`, `nh6`, `ll14`),
доставили датаграм **побайтово равным контролю**: снаружи отказ неотличим от
«правила не было». Третье — и это главное для письма: в ветви IPv6 у
списка есть клетка `(7,1)` «hop_limit», и на PPPoE-кадре она пишет байт 21,
то есть **младший байт поля PPP-протокола**: `0x0057` → `0x0090`, кадр
перестаёт быть пакетом IPv6 и уходит в очередь юнита (pppd), а `ppp0` при
этом всё равно считает его принятым — `dev_sw_netstats_rx_add()` стоит
**до** развилки по протоколу. Это первая измеренная клетка за проект, которая
меняет не поле, а **путь** кадра.

## 4. Отказ стража — не отбрасывание кадра

Пять плеч с `live = 0` доставили датаграм (`ipin = 1`, `udp4 = 18`), и
`rhex` каждого из них **побайтово равен** `rhex` контроля: кадр, ушедший на
дальнюю сторону, не отличается от контрольного. Это не мелочь: снаружи
отказ стража выглядит как «правила не было», и единственный способ увидеть
его — счётчик цепи, а не получатель. В прошлых ходах я записывал такие плечи
как «мёртвые»; мёртвая у них **запись**, а не кадр.

## 5. `@ll` достаёт до MAC источника и до ethertype — и второе ничего не решает

`@ll` на этом кадре ограничен 14 байтами (`nft_ll_write_ok`), то есть
заголовком Ethernet; заголовок PPPoE-сессии начинается с 14-го байта и
недостижим (`ll14`: `live = 0`). Зато `(6,2)` — это MAC источника, и после
записи `pppoe_rcv` не находит сессию: `__get_item()` ищет по
`(sid, h_source, ifindex)`, а `h_source` уже другой. `(13,1)` — младший байт
ethertype: на проводе `88 64` становится `88 ff`, и кадр всё равно доходит.
Разделяет эти два объяснения пара плеч:

| плечо | что на проводе | доставка |
|---|---|---|
| `ll13` (запись `0xff` в байт 13 на лету) | `88 ff` | **есть** (`udp4 = 18`) |
| `pre88ff` (те же байты снаружи, правила нет) | `88 ff` | **нет** (`udp4 = -1`, `ipin = 0`) |

Один и тот же кадр: отправленный с `0x88ff` извне он не PPPoE, а
переписанный по дороге — PPPoE. Значит `pppoe_rcv` вызывается по тому
`skb->protocol`, который `eth_type_trans()` записал **до** хука, и запись в
ethertype приёмный путь не видит вовсе.

`(7,1)` — это `offsetof(struct ipv6hdr, hop_limit)`, единственная клетка

`0x0090`, `proto_to_npindex()` возвращает `-EINVAL`, и `ppp_receive_nonmp_frame`
кладёт кадр в очередь **юнита**: `urn = 68` (весь кадр целиком),
`i6in = 0`. И рядом: `prx = 66` — `ppp0` считает кадр принятым, потому что
`dev_sw_netstats_rx_add()` стоит до развилки по протоколу. «Устройство
приняло 66 байт» и «стек не видел ничего» — одновременно и оба верны.
`hopsame` — та же клетка со значением самого байта: доставка, как у
контроля.

Остальные клетки списка IPv6 на этом кадре тоже попадают не туда, куда
обещают: `(0,4)` и `(2,2)` — это `ver/type`, `code` и **sid** PPPoE-сессии,
и после записи `pppoe_rcv` не находит сессию (`prx = 0`); `(8,16)` — это
**первые 16 байт заголовка IPv6** (версия, длина, next header, hop limit и
первые 8 байт saddr), а не saddr: запись тех же байтов ничего не меняет
(`hdr_same`), запись `0x90…` даёт версию 9 и `Ip6InHdrErrors = 1`
(`hdr_bad`). Настоящий saddr (смещение 16) и daddr (24 от заголовка) в
списке есть только как `8` и `24`, и оба ложатся на восемь байт раньше:
`(24,16)` — это `saddr[8..15] + daddr[0..7]`, после чего адрес перестаёт
быть локальным (`i6deliv = 0`). У IPv6 нет контрольной суммы заголовка,
поэтому здесь запись ловит не сумма, а проверка версии и таблица
маршрутизации.

| vlan | `op_vlan` | 1 | 1 | -1 | - |
| vlan | `hln_vlan` | 0 | 1 | 42 | ;0x1;0x2;aa:bb:cc:00:00:66;*;v1 |

`arc` — счётчик семейства `arp` на `NF_ARP_IN`, `repn` — длина ответа,
который ядро отправило обратно. Без устройства `arc = 0` и ответа нет;
с устройством `arc = 1`, ответ 42 байта, и `/proc/net/arp` называет
интерфейсом **`v1`** — то есть кадр действительно прошёл `vlan_do_receive()`
и попал в стек через vlan-устройство. `(8,2)` на однотеговом кадре
сдвига нет (метка уже в метаданных, ARP-заголовок начинается с 14-го
байта), поэтому запись ложится в `sha`, и ядро отвечает **написанному MAC**
(`90:91:cc:00:00:66`). `(6,2)=0x9091` проходит `arp_rcv()` и умирает в
`arp_process()` — счётчик 1, ответа нет. `(4,2)` список ARP запрещает:
`live = 0`, кадр доставлен нетронутым.

## 8. Ошибки хода, все мои

1. **Шесть предсказаний из двадцати трёх неверны, и пять из них — один и
   тот же класс.** Я записал «отказ стража ⇒ кадр не дойдёт» для `bare`,
   `trsaddr`, `trdaddr`, `nh6`, `ll14`. Измерено: кадр доходит и байты
   равны контролю. Отказ стража — это пропуск записи, а не вердикт о кадре.
2. **P17 неверно: запись в ethertype не убивает доставку.** Я ждал
   `ipin = 0`; измерено `ipin = 1`, `udp4 = 18`. Причина найдена не
   чтением, а парой `ll13`/`pre88ff`: приёмный путь судит по
   `skb->protocol`, записанному до хука.
3. **P25/P26 неверны по адресу.** Я описал клетку `(8,16)` как «настоящий
   saddr»; на самом деле запись `@nh` идёт от `skb_network_offset() = 14`,
   то есть в **первые 16 байт заголовка IPv6**. Поймал `Ip6InHdrErrors = 1`
   на плече, где я ждал доставку; плечи переименованы в `hdr_same` и
   `hdr_bad`, и в отчёте написано, что они пишут на самом деле.
4. **Плечо `tos`.** Запись `(1,1)` ложится в **код PPPoE** (байт 15), а не в
   `tos` IPv4 — и датаграм доходит. Я сам поставил его в группу «убитых
   контрольной суммой» в проверке, и проверка покраснела на верных данных;
   это была моя ошибка в проверке, а не в приборе.
5. **Шесть ошибок в самом верификаторе, все до первого числа в документе:**
   смещение записи `@ll` считалось как `14 + off` (для `@ll` это `off`);
   полезная нагрузка читалась как `ip[20:28]` (это заголовок UDP, магия
   лежит в `ip[28:36]`); хэш initrd искался среди двух полных прогонов;
   якорь `vlan_do_receive` искался не в том файле (это `net/8021q/vlan_core.c`);
   проверка детерминизма сравнивала MAC моста, который ядро выбирает заново
   при каждой загрузке (4 строки расходились на верных данных);
   и `live` в разделе `vlan` не печатался вовсе, так что «отказ» был неотличим
   от «доставки» — добавлен.
6. **Прибор:** первая сборка не собралась на инициализаторе структуры
   (`char dev[]` в плоском списке) — `-Wint-conversion`; вторая версия
   печатала `udp4`-байты и байты очереди юнита в один буфер (`hu`) — ровно
   ошибка F40 №2, поймана до запуска, разведены на `hux`/`hun`.

## 10. Что не измерено, прямо

Один хук (bridge prerouting), одна пара veth, один отправитель, один юнит,
один `sid`, один адрес на `ppp0`. **pppd не участвовал**: `PPPIOCATTCHAN` +
`PPPIOCCONNECT` без переговоров LCP, без CCP-сжатия, без `PPP_MP` — то
есть ветки `proto >= 0xc000`, `PPP_COMP` и мультилинка не тронуты (и
`crn = 0` во всех 36 плечах по той причине, что страж не может написать
байт PPP-протокола: `@ll` до него не достаёт, а в списках `@nh` его нет —
в IPv4; в IPv6 достаёт клетка `(7,1)`, но она пишет `0x0090`, а не `0xc0…`).
IPv6-стек получателя: сумма UDPv6 посчитана **прибором**, соседей и
маршрутизатора нет, `ICMPv6` не измерялся, `DAD` выключен
(`dad_transmits = 0`), чтобы не было шума. Не тронуты GSO/`CHECKSUM_PARTIAL`,
`@th` в состоянии `BOUND`, QinQ поверх PPPoE, настоящий `vlan`-фильтр моста.
`IpInReceives`/`Ip6InReceives` — глобальные счётчики: дельта на плечо могла
бы поймать посторонний пакет, поэтому каждый раз она читается в узком окне и
сверяется с моделью, а обе загрузки совпадают побайтово. Одна честная
строка про `pre88ff`: у него `live = 0` не потому, что страж отказал, а
потому что правила нет вовсе (цепь очищена).

**Не уязвимость**: правило ставит root в начальном user ns. Следствия,
измеренные здесь: молча не выполненная запись; запись, попадающая в поле
другого протокола (длина и sid PPPoE, код PPPoE, MAC источника); кадр,
который после клетки «ipv6 hop_limit» уходит в pppd вместо IP-стека, а
устройство всё равно считает его принятым; ARP-ответ, отправленный на MAC,
который выбрало правило.
