Theme: the transport base is the one base with no half-way state — and the
checksum it never pays for.

No diff below: the measurement names a cost the rule can pay (`csum type inet`)
and does not change the code that charges it.

Six measurements on Linux 7.3.4, nftables in the bridge prerouting hook, one
rule at a time, one frame at a time.  Four envelopes carry the same
IPv4/UDP datagram (10.1.0.1 -> 10.9.0.7:5000, 18 bytes of 0x77): bare
ethernet, one 802.1Q tag, Q-in-Q (0x88a8 + 0x8100), and a real PPPoE session
(eth | 0x8864 | sid 99 | 0x0021 | IPv4).  The receiving side is a real PPP
unit (`/dev/ppp`: PPPIOCNEWUNIT + PPPIOCATTCHAN + PPPIOCCONNECT, the PPPoX
socket moved to PPPOX_BOUND by PPPIOCGCHAN -- the pppd sequence without pppd),
two real UDP sockets (the original port and the port the rule writes), and the
kernel's own counters.  126 arms x 2 boots, byte-identical.

1. `@th` is exact or dead.  There is no third state.

nft_payload_eval() and nft_payload_set_eval() both take
`offset = nft_thoff(pkt)` for NFT_PAYLOAD_TRANSPORT_HEADER, and pkt->thoff is
built by one function, __nft_set_pktinfo_ipv4_validate():

        pkt->thoff = skb_network_offset(skb) + nhoff + iph->ihl*4

with the IP header read at `skb_network_offset + nhoff`.  Read and store share
the coordinate; the only question is whether pktinfo was built at all
(NFT_PKTINFO_L4PROTO).  Measured, 8 cells per cell block, two gates:

  envelope                     no `meta`   with `meta protocol`   the sport cell
  bare ethernet                 8/8 live        8/8 live          bytes 34..35
  802.1Q vid 100                8/8 live        8/8 live          bytes 34..35
  Q-in-Q 0x88a8+0x8100          0/8 live        8/8 live          bytes 38..39
  PPPoE session                 0/8 live        8/8 live          bytes 42..43

No cell is ever "half alive": none of the 64 grid cells is accepted and then
writes a byte other than the one its (offset,len) names.

2. A single 802.1Q tag does not shift the transport base at all.

skb_vlan_untag() runs in __netif_receive_skb_core() before any hook: the tag
goes to skb->vlan_tci, skb_reorder_vlan_header() moves the two MAC addresses
over it, and vlan_set_encap_proto() rewrites skb->protocol.  So at the hook the
frame has no tag in its bytes and `eth_hdr(skb)->h_proto` is already the inner
ethertype: nft_do_chain_bridge() takes the IPv4 branch on a tagged frame
without any help.  The 802.1Q column is the bare column, cell for cell, with
and without `meta protocol` -- and `meta protocol` is a no-op there because
nft_meta_pktinfo_may_update() returns at once when pkt->flags is set.

Q-in-Q keeps the inner tag in the bytes, so `eth_hdr()->h_proto` is 0x8100 and
the whole base is dead until `meta protocol` reads the encapsulated proto at
mac+16 and rebuilds pktinfo with nhoff = VLAN_HLEN.  PPPoE is the same story
with nhoff = PPPOE_SES_HLEN = 8.  Both then land on the true transport header.

3. The TCP doff guard is in the corrected coordinate system.

nft_th_write_ok() refuses cells overlapping `offsetof(struct tcphdr, ack_seq)
+ 4 = 12`.  On a TCP segment inside PPPoE with `meta protocol` exactly the same
four cells are refused as on a bare frame -- (10,4) (12,1) (12,2) (12,4) --
because thoff is now the real TCP header.  Without `meta protocol` all six
cells are refused: pktinfo is never built.  The guard cannot be fooled by the
envelope the way nft_nh_write_ok_ip4() is, where the list is written in the
coordinates of the field name and the store is not (F42).

4. Three bases, one cell, one packet.

The same `(offset,len) = (0,2)` store on the same PPPoE frame, with `meta
protocol`:

  @ll,0,2   accepted, changes frame bytes 0..1     (destination MAC)
  @nh,0,2   accepted, changes frame byte 15         (PPPoE ver/type+code; the
                                                     first byte stays 0x11 by
                                                     the case-0 value check)
  @th,0,2   accepted, changes frame bytes 42..43    (the real UDP sport)

Three coordinate systems in one packet.  The receiver separates them: the
frame whose destination MAC was rewritten never reaches the IP stack
(IpInDelivers 0, no datagram), while the frame whose PPPoE header was rewritten
is delivered intact -- pppoe_rcv() never looks at ver/type or code at all: it
gates on the length field and finds the session by
`__get_item(pn, ph->sid, eth_hdr(skb)->h_source, dev->ifindex)`.

5. `@th` can never reach the header that shifted it.

The smallest frame byte an accepted `@th` store touches is 42 on PPPoE and 38
on Q-in-Q, while the PPP protocol field sits at 20..21 and the inner Q-in-Q tag
at 16..19.  The store offset is thoff + priv->offset, offset >= 0, and thoff
already includes nhoff: the base is *behind* the header that moved it.  That is
why the 0xc000+ PPP protocol branch (pppd's channel queue) is unreachable from
a bridge rule through `@th` -- not for lack of a whitelist entry.

6. The checksum is a wall the guard does not see, and CSUM_INET is the toll.

A datagram with a real UDP checksum (0x08ad) and `@th,2,2` rewritten to port
5001:

  arm                            wire dport  csum   valid  UdpInErrors  delivered
  control                           5000     08ad    yes       0        5000
  store only                        5001     08ad    no       2 / 1    nowhere
  store + CSUM_INET (offset 6)      5001     08ac    yes      0        5001
  sport -> 0x9999 + CSUM_INET       5000     0b54    yes      0        5000
  store into the checksum field     5000     9091    no       2 / 1    nowhere
  the same + CSUM_INET              5000     9091    no       2 / 1    nowhere
  payload byte + CSUM_INET          5000     ef92    yes      0        5000
  payload byte, no CSUM_INET        5000     08ad    no       2 / 1    nowhere

The first line is the point: the guard accepts, the coordinates are exactly
right, the byte on the wire is the one the rule names -- and the receiver drops
the datagram, because the rule rewrote a field covered by the transport
checksum and did not pay for it.  (2 / 1: the bare frame is delivered twice,
once to the local stack and once up from the bridge; the PPPoE frame once.)

CSUM_INET is a separate action, not a consequence of the store:
`csum_offset = offset + priv->csum_offset` (thoff + 6) while the store is
`offset + priv->offset` -- two different bytes of the same expression, and the
0x08ad -> 0x08ac difference is exactly the 5000 -> 5001 increment.

And a store into the checksum field itself cannot be saved: the checksum
update runs first (nft_payload_csum_inet() -> skb_store_bits() of the field)
and skb_store_bits() of the payload follows, so the field ends up holding
exactly the immediate (0x9091 measured), and the datagram dies either way.
Order in one branch, measured rather than inferred.

7. IPv6 has no "not computed", so every unpaid transport write is fatal.

The same frame over IPv6 inside PPPoE (UDP header at byte 62): without `meta
protocol` the cells do not run and the datagram is delivered untouched; with
it, all four cells run and every one of them kills the datagram
(Udp6InErrors +1, nothing delivered).  With CSUM_INET at offset 6 the dport
rewrite is delivered to the *written* port.

Not a vulnerability: the rule is installed by root in the initial user
namespace.  The consequences are: a store that lands exactly in the field it
names and still destroys the datagram; a store into the checksum field that no
amount of checksum maintenance can save; and a dead cell block on any envelope
that moved the transport header, revived or not by one expression earlier in
the chain.

Not measured here: `@th` in the inet and netdev families, where thoff is built
by two other functions (nft_set_pktinfo_ipv4() uses ip_hdrlen() without
skb_network_offset, ..._ingress() uses ihl*4); a tagged PPPoE frame; SCTP and
ICMP checksum types; CHECKSUM_PARTIAL/GSO; the pseudo-header flag
(NFT_PAYLOAD_L4CSUM_PSEUDOHDR) on a saddr/daddr store; conntrack and
defragmentation.

===== SUMMARY.md =====
# F43 — транспортная база `@th`: три системы координат и чек-сумма, которую страж не платит

Ядер не собирал: весь ход на том же `7.3.4-T563` (`1efbc957…2033`, образ F41),
на котором мерили F41 и F42. Новый только прибор `differ565` — **126 плеч в
каждой из двух загрузок**, `141` строка `F565` на загрузку, обе загрузки
совпадают побайтово (`differing = 0`).

## 1. Ответ на вопрос, который 564-й оставил открытым

564-й кончился фразой: «открывает ли `@th` в bound-состоянии третью систему
координат, которая достаёт до байта PPP-протокола». Ответ — **нет, и не по
списку клеток, а по построению**: `@th` — единственная база, которая либо
мертва (счётчик 0), либо попадает точно в поле, которое называет. У неё нет
половинчатого состояния, поэтому она не может «промахнуться на заголовок» —
и ровно поэтому не может достать до сдвинувшего её заголовка (`§7`).
Измерено: 48 живых клеток из 64 в сетке четырёх конвертов × двух gate.

## 2. Конверты: где на самом деле стоит транспортный заголовок

Кадры разобраны из собственных байтов лога (`F565 FRAME`), не из литералов:

| конверт | кадр на проводе | кадр в хуке | `eth_hdr()->h_proto` | `skb->protocol` | IP | UDP |
|---|---|---|---|---|---|---|
| `p` голый | 60 | 60 | 0x0800 | 0x0800 | 14 | **34** |
| `w` 802.1Q | 64 | **60** | **0x0800** | 0x0800 | 14 | **34** |
| `q` Q-in-Q | 68 | 64 | 0x8100 | 0x8100 | 18 | **38** |
| `ps` PPPoE | 68 | 68 | 0x8864 | 0x8864 | 22 | **42** |
| `ps6` IPv6 в PPPoE | 88 | 88 | 0x8864 | 0x8864 | 22 | **62** |
| `pt` / `pst` TCP | 72 / 80 | 72 / 80 | 0x0800 / 0x8864 | — | 14 / 22 | 34 / **42** |

Одна метка 802.1Q из кадра **уходит до хука** (`skb_vlan_untag()` →
`skb_reorder_vlan_header()`), поэтому в хуке от неё не остаётся ни байта:
кадр равен голому, а `eth_hdr()->h_proto` — уже внутренний `0x0800`. Q-in-Q
теряет только внешнюю метку, внутренняя остаётся в байтах, и `h_proto`
равен TPID `0x8100`.

## 3. Сетка: `@th`, 8 клеток, два gate

| конверт | gate 0 | gate 1 | `t0_2` (sport) при g0 | при g1 | `t16_2` при g0 | при g1 |
|---|---|---|---|---|---|---|
| `p` | **8/8** | **8/8** | 34,35 | 34,35 | 50,51 | 50,51 |
| `w` | **8/8** | **8/8** | 34,35 | 34,35 | 50,51 | 50,51 |
| `q` | **0/8** | **8/8** | — | 38,39 | — | 54,55 |
| `ps` | **0/8** | **8/8** | — | 42,43 | — | 58,59 |

Что видно только вместе: **802.1Q не сдвигает `@th` вовсе** — таблица `w`
совпадает с `p` клетка в клетку и при `meta protocol`, и без неё, потому что
метка ушла из байтов ещё до хука. А два конверта, которые действительно
сдвигают базу (`q` и `ps`), без `meta protocol` не дают ни одной живой клетки,
и оживают целиком от одной экспрессии: `meta` пересобирает pktinfo через
`nft_meta_pktinfo_may_update()` → `__nft_set_pktinfo_ipv4_validate(pkt, nhoff)`
с `nhoff = VLAN_HLEN` (4) или `PPPOE_SES_HLEN` (8), а `thoff` считается уже от
исправленного `nhoff`. Мёртвых по одному, «наполовину живых» клеток нет ни в
одном конверте.

## 4. Почему у `@th` нет половинчатого состояния

`nft_payload_eval()` и `nft_payload_set_eval()` в ветви
`NFT_PAYLOAD_TRANSPORT_HEADER` берут **одно и то же** выражение
`offset = nft_thoff(pkt)`, в обе стороны, и обе проверяют
`pkt->flags & NFT_PKTINFO_L4PROTO`. Это и есть отличие от `@nh`, где чтение
прибавляет `pkt->nhoff`, а запись — нет (F40, F42): там одна база живёт в двух
системах координат одновременно, здесь — только в одной, зато «всё или
ничего». В том же файле ровно два вхождения `offset = nft_thoff(pkt);` — это
проверяет верификатор, а не глаз.

## 5. TCP: страж живёт в исправленной системе координат

`nft_th_write_ok()` запрещает клетки, перекрывающие `ack_seq`
(`doff = offsetof(struct tcphdr, ack_seq) + 4 = 12`) — и на PPPoE-кадре этот
запрет попадает в **настоящий** `ack_seq`, потому что `thoff` уже исправлен.

| плечо | живых | мёртвые |
|---|---|---|
| `pt` TCP, gate 0 | **2/6** | (10,4) (12,1) (12,2) (12,4) |
| `pst` TCP в PPPoE, gate 0 | **0/6** | все шесть — pktinfo не собран |
| `pst` TCP в PPPoE, gate 1 | **2/6** | (10,4) (12,1) (12,2) (12,4) — те же четыре, клетка в клетку с `pt` |

То есть на PPPoE у `@th` **и страж, и запись** в правильной системе координат —
в отличие от `@nh`, где список разрешает клетку, а запись уходит на восемь
байт раньше (F42).

## 6. Три базы, одна клетка `(0,2)`, один и тот же PPPoE-пакет

| база | жив | байты кадра, которые изменились | `IpInDelivers` | `recv()` на 5000 |
|---|---|---|---|---|
| `@ll,0,2` | 1 | **0,1** (MAC назначения) | 0 | — |
| `@nh,0,2` | 1 | **15** (байт 14 остался прежним: `0x11`→`0x11`) | 1 | 18 |
| `@th,0,2` | 1 | **42,43** (настоящий sport) | 1 | 18 |

Три базы — три разные системы координат на одном пакете. И два следствия,
которые видны только по приёмной стороне: кадр с переписанным MAC назначения
до IP-стека не доходит вовсе (0), а кадр с переписанным PPPoE-заголовком
доходит и доставляется — `pppoe_rcv()` не смотрит ни на ver/type, ни на code
вовсе: он проверяет длину (`skb->len < len`) и ищет сессию по
`__get_item(pn, ph->sid, eth_hdr(skb)->h_source, dev->ifindex)`.

## 7. Чего `@th` не может достать никогда

Минимальный байт кадра, до которого дотягивается принятая запись `@th`:
**42** на PPPoE-кадре (`q`: **38**). Байт PPP-протокола лежит в 20..21,
внутренняя метка Q-in-Q — в 16..19. `@th` не может писать «назад»: `offset`
неотрицателен, а `thoff` уже включает `nhoff`. Поэтому канал `0xc000+`
(очередь pppd) из правила моста через `@th` недостижим — не потому, что клетки
нет в списке, а потому, что база стоит **за** этим заголовком.

## 8. Чек-сумма: страж пропускает, координаты верны, датаграм не доходит

Датаграм с **настоящей** UDP-чек-суммой (`0x08ad`), одна и та же запись
`@th,2,2 = 5001`, два конверта:

| плечо | dport на проводе | поле csum | чек-сумма | `Udp InErrors` | куда доставлено (голый / PPPoE) |
|---|---|---|---|---|---|
| `ctl` | 5000 | `08ad` | верна | 0 / 0 | **5000** / **5000** |
| `dp_nc` без пересчёта | **5001** | `08ad` | **неверна** | **2 / 1** | никуда / никуда |
| `dp_cs` `csum type inet`, off 6 | **5001** | **`08ac`** | верна | 0 / 0 | **5001** / **5001** |
| `sp_cs` sport → `0x9999` | 5000 | `0b54` | верна | 0 / 0 | 5000 / 5000 |
| `ck_nc` пишет само поле csum | 5000 | **`9091`** | неверна | 2 / 1 | никуда / никуда |
| `ck_cs` то же + пересчёт | 5000 | **`9091`** | неверна | 2 / 1 | никуда / никуда |
| `pay_cs` байт полезной нагрузки | 5000 | `ef92` | верна | 0 / 0 | 5000 / 5000 |
| `pay_nc` то же без пересчёта | 5000 | `08ad` | неверна | 2 / 1 | никуда / никуда |

Три вещи, которые видны только вместе.

1. **Запись принята, координаты верны, байт на проводе — и датаграм всё равно
   умирает.** Это первый раз за проект, когда «принято» и «доставлено»
   расходятся не из-за промаха на заголовок, а из-за поля, которое правило не
   тронуло. Страж чек-сумму не считает никогда; считает стек — и только он.
2. **`csum type inet` — это отдельное действие, а не следствие записи.**
   `csum_offset = offset + priv->csum_offset` (то есть `thoff + 6`), а сама
   запись идёт по `offset + priv->offset`: два разных байта одной экспрессии.
   Разница `08ad → 08ac` — ровно инкремент от `5000 → 5001`.
3. **В само поле чек-суммы пересчёт не спасает.** `ck_cs` кладёт в поле
   `0x9091` — не «пересчитанную» сумму, а ровно иммедиат: `nft_payload_csum_inet()`
   считается **до** `skb_store_bits()` и затирается записью. Порядок в одной
   ветви, и он измерен, а не выведен.

## 9. IPv6: там нулевой чек-суммы не бывает

| gate | клетки `@th` | живых | что у получателя |
|---|---|---|---|
| 0 | (0,2) (2,2) (6,2) (8,2) | **0/4** | правило не сработало, датаграм доставлен на 5000 |
| 1 | те же | **4/4** | все четыре роняют датаграм: `Udp6InErrors` +1, доставок 0 |
| 1 | `dp_nc` (dport 5001, без пересчёта) | 1 | `Udp6InErrors` +1, доставок 0 |
| 1 | `dp_cs` (dport 5001, `csum type inet`) | 1 | **доставлен на 5001** |

Все клетки, записанные без пересчёта, убивают датаграм — и это не «строже,
чем в IPv4», а свойство протокола: нулевая контрольная сумма в IPv6
нелегальна, поэтому «не считали» здесь не проходит.

## 10. Ошибки хода, все мои

1. **`f564_udp6_csum(v6, 26)` вместо `v6 + 14`** — помощник ждёт указатель на
   заголовок IPv6, я дал начало кадра; контрольная сумма вышла неверной, и
   контрольное плечо IPv6 не доставило ничего (`i6in = 1`, сокет молчит).
   Поймал дым до первого числа в отчёте.
2. **`nh0` с иммедиатом `0x9091` отказан**: `case 0` белого списка сравнивает
   первый байт значения с `data[0]`, а там `0x11` (ver/type PPPoE) — клетка
   мертва, и я чуть не записал в таблицу «достижимости» пустоту. F40 это уже
   знал; исправлено на `0x1191`, плечо перезапущено.
3. **IPv6-сокет на 5001 привязан раньше, чем `f564_ppp6_setup()` поднял адрес
   на `ppp0`** (`EADDRNOTAVAIL`, `-99`): дым `f565v` показал `u6_5001 = -1` на
   всех плечах при живых записях, и я чуть не записал «запись не доставлена».
   Привязка перенесена после `f564_ppp6_setup()`; v4-сокет с самого начала
   привязан после подъёма юнита, там ошибки не было.
4. **Верификатор: `filesize` в cpio прочитан по смещению 102 вместо 54** —
   третий раз за проект эта семья ошибок; бинарник «не находился» в initrd.
5. **Верификатор: чек-сумма проверялась с обнулённым полем и сравнением с
   `0xffff`** — так нельзя: с обнулённым полем выходит дополнение суммы. 13
   красных проверок **на верных данных**, прежде чем я перестал верить
   прибору и посчитал сумму вручную.
6. **Верификатор: смещение записи `@nh` смоделировано как `hook_ip + off`**
   вместо `14 + off` (в хуке `skb_network_offset() == 0`), и «достижимость»
   `nh0` показала 22 вместо 14.
7. **Верификатор падал `min()` на пустом списке** — нашёл селфтест: мутация
   `dead_to_live` уронила скрипт, а крэш не считается пойманной мутацией.
8. **Верификатор сравнивал только записанные байты** и не ждал изменения поля
   чек-суммы в плечах с пересчётом; теперь ожидаемый кадр строится целиком
   (запись + пересчитанная сумма) и сравнивается побайтово.
9. **`ctl` печатает `gate=0`**, а искал я его с `gate=1` — «missing arm» на
   верных данных в двух секциях.

## 11. Предсказания: 15 из 15 — и это тоже результат

`research/predictions_565.md` написан **до** прибора. Сошлись все пятнадцать,

## 12. Что не измерено, прямо

Один хук (bridge prerouting), одна veth-пара, один отправитель; UDP и TCP над
IPv4 и UDP над IPv6 в PPPoE — больше протоколов нет. **Не тронуто:** `@th` в
семействах `inet` и `netdev`, где `thoff` считают две другие функции
(`nft_set_pktinfo_ipv4()` даёт `ip_hdrlen()` без `skb_network_offset`,
`..._ingress()` — `ihl*4`), то есть там возможна третья формула; помеченный
PPPoE-кадр (пересечение `w` и `ps`); SCTP и ICMP-типы пересчёта
(`NFT_PAYLOAD_CSUM_SCTP`, `icmphdr`); `CHECKSUM_PARTIAL`/GSO; пересчёт
псевдозаголовка (`NFT_PAYLOAD_L4CSUM_PSEUDOHDR`) при записи в saddr; QinQ с
`0x9100`; conntrack и дефрагментация. Отдельно: в плече `dp_nc` на проводе
изменился только байт 37, а не 36–37 — потому что первый байт иммедиата
(`0x13`) совпал с прежним старшим байтом dport; это свойство значения, а не
неполной записи, и модель сравнивает именно изменённые байты.

**Не уязвимость**: правило ставит root в начальном user ns. Следствия —
запись, которая попадает точно в поле и всё равно убивает датаграм
(чек-сумма), запись в само поле чек-суммы, которую не спасает пересчёт, и
мёртвая клетка на конверте, который сдвинул базу.
