STATUS: NOT SENT. Follow-up to the F28 report; no patch is proposed.

Theme: on a device that has no link-layer header, the `@ll` base does not
collapse onto `@nh` -- it disappears -- and the same `@nh` cell that is
refused at one door is a single byte of the header at another.

No diff below: this measures the guards as they stand and proposes no change.

Linux 7.3.4, nftables in the initial user namespace, one packet at a time, one
rule at a time.  One frame, 88 bytes: ethernet | PPPoE session header (sid 99) |
PPP protocol `00 57` | IPv6/UDP 40000->5000.  A PF_PPPOX session socket bound on
a veth, a ppp unit attached to it exactly as pppd does it
(`PPPIOCGCHAN`/`PPPIOCNEWUNIT`/`PPPIOCATTCHAN`/`PPPIOCCONNECT`), the frame
injected on the peer.  The kernel removes the eight bytes of
PPPoE+PPP before the layer-3 hook, so the same frame is presented to four doors
in one boot: `inet` prerouting and `ip6` prerouting on ppp0, the netdev ingress
hook on the veth, and an `ip` prerouting chain that never sees it.

At the layer-3 doors `skb_network_offset()` is 0 and `pkt->nhoff` is 0: `@nh,0,4`
reads `60 00 00 00`, `@nh,4,2` the payload length, `@nh,7,1` the hop limit `40`.
At the netdev ingress door the same cells read `11 00 00 63` (the PPPoE header)
and `57` (the PPP protocol byte).  So `nft_meta_pktinfo_may_update()` adds its
`PPPOE_SES_HLEN` bytes only at doors that see the frame *before* `ppp_input()`;
once the PPP layer has run, no constructor has anything to add.

`@ll` on ppp0 is not a base at all.  `ppp_receive_nonmp_frame()` resets
`mac_header` to `skb->data`, the receive path calls `skb_reset_mac_len()`
(`net/core/dev.c`), so `skb_mac_header_len()` is 0 while
`skb_mac_header_was_set()` is true -- and `nft_payload_eval()` refuses the LL
base on `skb_mac_header_len(skb) == 0`.  Every `@ll` read and every `@ll` write
on ppp0 is refused, including `@ll,0,1`, which the ethernet layer-3 doors accept.
The log agrees twice and inconsistently: `NFULA_L2HDR` is absent (it is gated on
`pf == NFPROTO_NETDEV || NFPROTO_BRIDGE`), while `NFULA_HWHEADER` is present and
carries `dev->hard_header_len` = 22 bytes taken from `skb_mac_header()` -- that
is, the first 22 bytes of the IPv6 header, labelled as the hardware header of a
device of type `ARPHRD_PPP`.

The guard at both layer-3 doors is `nft_nh_write_ok_ip6()` (`pf` is
`NFPROTO_IPV6` in the `inet` family as well).  It is a whitelist: `(4,2)` payload
length and `(6,1)` next header are refused, `(7,1)` hop limit, `(2,2)`, `(8,16)`
and `(24,16)` are accepted, and `case 0` accepts only an immediate whose high
nibble is 6 -- the value, not the length.  The same frame at the netdev ingress
door goes through the constant `true` of `NF_NETDEV_INGRESS`, so `@nh,7,1 = 0x90`
there rewrites the PPP protocol field, `ppp_receive_nonmp_frame()` hands the
frame to the unit queue, and `dev_sw_netstats_rx_add()` has already counted 66
bytes on ppp0 while `Ip6InReceives` stays 0.  Five single-cell writes at that door
die invisibly: the PPPoE length (the `skb->len < len` test in `pppoe_rcv()`), the
session id and the source MAC (`__get_item()`), the protocol byte
(`ppp_skb_is_compressed_proto()`), and the hop limit (the unit queue).  Controls
with the value the frame already carries are delivered, so it is the value and
not the act.

`@th` reaches the same byte by two formulas: `0 + 40` at the layer-3 doors and
`8 + 40 = 48` at the netdev ingress door after `meta protocol` rebuilt the
pktinfo.  `meta protocol` on a PPPoE frame returns the *inner* ethertype
(`0x86dd`) because it asks `nf_flow_pppoe_proto()`, and asking it is also what
makes `@th` usable at that door; without it `pkt->flags` is 0 and the base is
refused.  With `csum type inet` and `csum_offset 6` both doors deliver the
datagram to the written source port 37009.

Two silent non-events, in the same family as the F28 report: a `csum type inet`
request on the `@nh` base in IPv6 neither fixes anything nor fails --
`nft_payload_csum_nh_write_ok()` returns `false` inside an `&&`, the store lands
and the datagram is delivered with an unmodified checksum request; and a write
to `daddr` that the whitelist allows loses the packet at the route lookup with
`Ip6InNoRoutes` and no other counter moving.

Not a vulnerability: the rules are installed by root in the initial user
namespace.  The report is about a base that ceases to exist on devices without a
link header, about a log attribute that reports IPv6 bytes as a hardware header,
and about a guard whose verdict for the same cell depends on the door.

# F49 — у двери на ppp0 база верна, а `@ll` не существует: одно выражение, три двери, три стражи

В 570-м я записал: «осталась одна дверь, где тот же кадр мог бы дойти до
`nft_nh_write_ok_ip6()` с `pf = NFPROTO_IPV6` и `nhoff = 22` — семейство `inet`
на layer-3». Ядер не собирал: весь ход на том же `7.3.4-T563`
(`1efbc957…2033`), образ F41..F48. Новый прибор `differ571` — **71 плечо в
каждой из двух загрузок**; все производные факты двух загрузок совпадают
(расходятся только MAC, которые ядро выбирает заново при каждой загрузке).

Кадр не собран руками: сокет сессии `PF_PPPOX` (sid 99) привязан на x1,
`PPPIOCGCHAN` + `PPPIOCNEWUNIT` + `PPPIOCATTCHAN` + `PPPIOCCONNECT` вешают
канал на юнит (как pppd, но без pppd), `ppp0` поднят с адресом `fd02::91/128`,
на нём UDP-сокет на 5000. На x0 уходит `AF_PACKET`-кадр 88 байт:
ethernet (14) | заголовок сессии PPPoE (6) | PPP-протокол `00 57` (2) | IPv6 +
UDP 40000→5000 + 18 × `0x77`. Восемь байт снимает **ядро**, а не прибор, — и
один и тот же кадр предстаёт перед четырьмя дверями одной загрузки:

| дверь | семейство | хук | устройство |
|---|---|---|---|
| `in3` | `inet` | prerouting (layer 3) | ppp0 |
| `ip63` | `ip6` | prerouting (layer 3) | ppp0 |
| `nd1` | `netdev` | ingress | x1 |
| `ip43` | `ip4` | prerouting | — (кадр сюда не приходит) |

## 1. Долг опровергнут: на layer-3 двери `nhoff = 0`, а не 22

Плечо узнаёт байт только одним способом — `cmp` с тем, что кадр несёт на самом
деле; `lives = 1` значит «дверь видит ровно эти байты в этой клетке».

Восемь байт, которые `nft_meta_pktinfo_may_update()` прибавляет для PPPoE,
живут **только на двери, которая видит кадр до декапсуляции**. На ppp0
`skb_network_offset() = 0`, `nhoff = 0`, `@nh,0,4` — настоящий заголовок IPv6, а
`@nh,7,1` — hop limit `40`; байт `57` (поле PPP-протокола), который та же клетка
читает на `nd1`, здесь **не совпадает**. Тот же байт `0x57` на двери `nd1`
лежит не там, где его ждёт слой 3, а на своём месте.

Механика, по которой это происходит (прочитана, а не выведена из чисел):
`pppoe_rcv()` снимает 6 байт заголовка сессии, `ppp_receive_nonmp_frame()`
снимает 2 байта PPP-протокола и **переставляет** `mac_header` на `data`, а вход
в приёмный путь (`__netif_receive_skb_core()`) сбрасывает `network_header` на
`data` — поэтому в момент хука обе базы совпадают с началом IPv6. Никакой
«третьей формулы» на этой двери нет: конструктор `thoff` идёт обходом
(`ipv6_find_hdr()`), а `nhoff` — ноль.

## 2. `@ll` на устройстве без L2 не сжимается в `@nh` — он исчезает

`nft_payload_eval()` для `NFT_PAYLOAD_LL_HEADER` первым делом требует
`skb_mac_header_was_set()` **и** `skb_mac_header_len() != 0`. На ppp0 второй
условие ложно: `__netif_receive_skb_core()` вызывает `skb_reset_mac_len()`,
а `mac_len = network_header − mac_header = 0 − 0 = 0`. Поэтому на layer-3 двери
отказаны **все** клетки `@ll` — и чтения (`ll0`, `ll4`, `ll8`), и записи
(`ll0_1`, `ll0_2`, `ll7_1`), включая `@ll,0,1`, которую на ethernet-двери
F44 принимала. На `nd1` та же клетка читает MAC назначения.

Лог об этом рассказывает двумя разными атрибутами, и они расходятся:

<!-- T6 -->
### T6  what the log carries about L2 at each door

| door | NFULA_L2HDR | NFULA_HWTYPE | NFULA_HWLEN | NFULA_HWHEADER |
|---|---|---|---|---|
| `in3` (ppp0) | 0 B | 512 | 22 | 22 B: `60000000001a1140fd02000000000000000000000000` |
| `ip63` (ppp0) | 0 B | 512 | 22 | 22 B: `60000000001a1140fd02000000000000000000000000` |
| `nd1` (x1) | 14 B | 1 | 14 | 14 B: `7623ee7a4ed53e09867e72578864` |
<!-- /T6 -->

`NFULA_L2HDR` ставится только при `pf == NFPROTO_NETDEV || NFPROTO_BRIDGE`
(`nfnetlink_log.c`), поэтому на layer-3 двери его нет вовсе — и это моя
поправка к F44: там я прочитал его отсутствие как «заголовка нет», а оно
означает «pf не тот». А `NFULA_HWHEADER` **не** закрыт никаким `pf`: он
копирует `dev->hard_header_len` байт от `skb_mac_header()`, и на ppp0 это
**22 байта заголовка IPv6**, подписанные как hardware header устройства типа
512 (`ARPHRD_PPP`). Один и тот же лог в одном и том же сообщении не говорит
про L2 ничего (L2HDR нет) и говорит неправду (HWHEADER = IPv6).

## 4. Одно выражение, три двери

`@nh,7,1 = 0x90` на **одном и том же кадре**:

### T3  one expression, three doors: `@nh,7,1 = 0x90` on the same frame

| door | cntp | lives | byte at the cell | ppp0 rx | Ip6InReceives | delivered |
|---|---|---|---|---|---|---|
| netdev ingress on x1 | 1 | 1 | `90` | 66 B | 0 | 0 |
| inet prerouting on ppp0 | 1 | 1 | `90` | 66 B | 1 | 1 |
| ip6 prerouting on ppp0 | 1 | 1 | `90` | 66 B | 1 | 1 |

На `nd1` байт `90` ложится в поле PPP-протокола (`00 57` → `00 90`), и
дальше `ppp_receive_nonmp_frame()` уводит кадр в очередь юнита:
`dev_sw_netstats_rx_add()` уже посчитал **66 байт** на ppp0, а `Ip6InReceives`

двум разным счётчикам сразу. На layer-3 дверях тот же байт — hop limit, и
датаграм доставляется.

Контроли, без которых это ничего не стоит (та же дверь `nd1`, то же
выражение, то же значение из кадра): `nh7_same` (`57`) доставлен, `nh7_90`
(`90`) — нет; `nh4_2_same` (`0044`) доставлен, `nh4_2_len` (`9091`) — нет.
Смерть делает **значение**, а не действие.

## 5. `@th`: две формулы, один байт

<!-- T4 -->
### T4  `@th` on the same frame: two formulas, one byte

| door | pktinfo | thoff | read `@th,0,2` | write, no csum | write + csum |
|---|---|---|---|---|---|
| `in3` | nhoff = 0 | 40 | `9c40` | Udp6InErrors | sport 37009, delivered |
| `ip63` | nhoff = 0 | 40 | `9c40` | Udp6InErrors | — |
| `nd1` | nhoff = 8 | 48 | `9c40` | — | sport 37009, delivered |
<!-- /T4 -->

Транспортный байт на проводе один (кадр 62), а путь к нему — разный:
на layer-3 двери `thoff = 0 + 40`, на `nd1` — `nhoff = PPPOE_SES_HLEN (8) + 0`
и `thoff = 8 + 40 = 48`, то есть `data + 48` у `nd1` и `data + 40` у `in3` —
один и тот же байт кадра. На `nd1` эта координата существует **только** если
правило спросило `meta protocol`: `meta protocol` на PPPoE-кадре возвращает
`0x86dd` (внутренний ethertype из `nf_flow_pppoe_proto()`), и тот же вызов
пересобирает pktinfo с `nhoff = 8`. Без него `@th` отказан — `pkt->flags = 0`.

Отсюда же — то, что на этой двери `meta protocol` = `0x86dd`, а не `0x8864`
(мой P9 был неверен), и `meta nfproto` = 5, а на layer-3 = 10.

## 6. Долг «три формы с `tapn = 0`»: это был фильтр, а не провод

<!-- T7 -->
### T7  the tap debt: the same frames, two filters

| shape | frames on the tap | old filter | shape-aware filter |
|---|---|---|---|
| `bare` | 1 | 1 | 1 |
| `hbh` | 1 | 0 | 1 |

Фильтр F48 (`f569_tap6()`) требовал, чтобы байт 20 кадра был `17`; при
hop-by-hop там `0`, поэтому кадр отбрасывался ещё до проверки иглы — и
`tapn = 0` у трёх форм был свойством прибора. Фильтр, который идёт по цепочке
next-header, на **том же** кадре и **том же** тапе считает 1. Провод нёс кадр
всё время.

## 7. Ошибки хода, все мои

1. **Верификатор объявил «IPv6 payload length 66»** — 66 это размер пакета, а
   в поле длины 26. Красным стало контрольное плечо, а не догадка.
2. **`dst6 = fr[38:54]`** — это `saddr[8..15] + daddr[0..7]`; модель объявила
   «нет маршрута» каждой доставленной датаграме. Поймали контрольные плечи.
3. **Тихие плечи неотличимы от быстрых**: у модели не было признака «кадр не
   отправлялся», и два контрольных плеча дали по 17 расхождений. Добавил в
   прибор поле `snt`, а не вывел его из имени плеча.
4. **Модель не считала `nft_payload_csum_inet()`** — два плеча с пересчётом
   ожидались мёртвыми, а они доставлены. Ещё одна причина печатать `csum/cso`.
5. **NFULA_HWHEADER прочитан как HWLEN и наоборот**: в этом ядре порядок
   `HWTYPE=15, HWHEADER=16, HWLEN=17`, а не как я предположил. Поймал первый
   дым: «HWLEN = 24576» — это `0x6000`, то есть первые два байта IPv6.
6. **`f571_tap_new()` шёл от `14 + 6`** вместо `14 + 40` — нашёл, читая код
   перед первым запуском.
7. **Буфер `post` был 80 символов (39 байт)** — транспортный заголовок с
   offset 40 в лог не попадал. Расширил до 300.
8. `u6sport` читался из байтов 8..9 **полезной нагрузки** (`0x7777`) вместо
   адреса из `recvfrom()`.
