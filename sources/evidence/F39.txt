Subject: nft payload set: the network-base guard is keyed on a field the receive
path fills, and a two-tag frame falls between two of its answers

`nft_payload_set_eval()` refuses a network-base store unless
`nft_nh_write_ok()` allows the (offset, length) pair.  Which branch of that
function judges the store is decided by `pkt->ethertype`, which for the bridge
family is `skb->protocol` -- the encapsulated protocol the receive path wrote
into the skb.  Measured on 7.3.4 with a bridge and two veth pairs:

1. A 802.1Q frame and a 802.1AD (0x88a8) frame are indistinguishable to every
   branch of the guard: the packet-relative 36-cell grid is the same 25 cells in
   both, and the network-base 40-cell grid is the same 14 cells.  `eth_type_vlan()`
   knowing two TPIDs changes no verdict.

2. A Q-in-Q frame (88a8 8100 0800 ...) is refused by all 40 network-base cells,
   because a single `skb_vlan_untag()` has popped the outer tag and left
   `skb->protocol == 0x8100`; `nft_nh_write_ok_bridge()` has no case for that, so
   `default: return false`.  In the same packet, `meta protocol` reports 0x0800:
   `nft_meta_pktinfo_may_update()` reads `h_vlan_encapsulated_proto` at
   `mac_header + 16`, which after the single pop is the real ethertype.  So the
   guard says "no protocol", `meta protocol` says "ipv4", and the IP stack never
   sees the frame.

3. `pkt->ethertype` is not read-only.  A `meta protocol` expression placed before
   the store in the same rule rewrites it to 0x0800, and the same 40-cell grid
   goes from 0 live cells to 12; the other two cells of the IPv4 list stay dead
   because their value checks read the packet at `skb_network_offset+0` and `+9`,
   where a Q-in-Q frame now carries the inner tag's TCI and the IPv4 id.
   Every store that goes live lands four bytes before the field it names:
   `@nh,8,1` writes the id high byte, not the ttl.  The reason is one line of
   asymmetry: `nft_payload_eval()` computes `skb_network_offset(skb) + pkt->nhoff`
   and `nft_payload_set_eval()` computes `skb_network_offset(skb)`.

4. On the way out, whether a stored `skb->vlan_proto` reaches the wire depends on
   two feature bits, not one: `vlan_hw_offload_capable()` tests
   `NETIF_F_HW_VLAN_CTAG_TX` for 0x8100 and `NETIF_F_HW_VLAN_STAG_TX` for 0x88a8,
   and veth advertises both.  With only the CTAG bit cleared, a
   `(12,2) = 0x88a8` store leaves nothing on the wire at all; with both cleared
   the frame leaves as `88a8 0064 0800 ...` and the peer pops it back.  A
   `(12,2) = 0x0000` store leaves `0000 0064` on the wire in every state.

5. The receive path pops exactly one tag per skb, because `skb_vlan_untag()`
   returns immediately when `skb_vlan_tag_present(skb)` is already true.  A
   Q-in-Q frame arriving from the wire therefore keeps its inner tag in the bytes
   (the far tap shows 64 bytes starting `8100 00c8 0800 ...`) and its protocol
   stays 0x8100: it is never delivered to IPv4.

No memory-safety claim is made, and none is implied: the rules in all of the
above need CAP_NET_ADMIN in the initial user namespace.  The consequences are
silently unapplied stores, frames that leave with a forged or vanished tag, and
stores that land four bytes away from the field they name while the rule's own
counter reports success.

Reproducer and per-cell tables: F39 in the same tree as F29-F38.

# F39 — второй TPID: 802.1AD и кадр с двумя метками

## Что спрошено

F38 кончился строкой «в `eth_type_vlan()` два значения, и я измерил только одно».
Вопрос, который оттуда следует, — не косметика: `0x88a8` (802.1AD) — это второй
TPID, который приёмный путь признаёт меткой; если снятие одноуровневое, то
QinQ-кадр после него несёт в байтах вторую метку, `skb->protocol` равен `0x8100`,
и оболочка для стража снова другая. Плюс второй вопрос того же хода: переживает
ли `vlan_proto = 0x88a8` дорогу наружу, если F37 показал, что ноль не переживает.

**Ядро то же.** `7.3.4-T558`, sha `459f02a5…` — тот же образ, которым мерили
F36, F37 и F38 (sha в шапке лога F38 и в шапке лога F39 совпадают). Ни одного
нового ядра этот ход не собрал; новый только прибор — `vm/differ561_add.c`,
собранный из differ560 с переименованным `main()`. Все помощники (netlink,
veth/bridge, AF_PACKET, чтение счётчика, ethtool) — те же байты, что в F31–F38.

**Прибор.** Шесть представлений одного и того же IPv4-датаграмма
(ihl 5, proto 17, 18 байт `0x77` в полезной нагрузке):

| имя | что в кадре | длина |
|---|---|---|
| `p` | голый ethernet + IPv4 | 60 |
| `w` | одна метка `8100`/`0064` | 64 |
| `s88` | одна метка `88a8`/`0064` | 64 |
| `q` | `88a8`/`0064` + `8100`/`00c8` | 68 |
| `q81` | `8100`/`0064` + `8100`/`00c8` | 68 |
| `x91` | `9100`/`0064` | 64 |

**Счёт.** Две полные загрузки одной батареи (`rep1`, `rep2`, один initrd,
577 строк `F561` каждая) и две отдельные загрузки одного режима `f561far`
(`farA`, `farB`) — эта секция в батарее стоит первой и несёт шум загрузки, §8.
Оракул каждой записи — счётчик самого правила, прочитанный до и после одной
отправки; каждая клетка сверена побайтово с контролем того же представления.

## 1. `meta protocol` называет QinQ-кадр IPv4

Одно правило `meta protocol` + `cmp eq <значение>` + счётчик, восемь кандидатов
на представление, один пакет на плечо:

| представление | `meta protocol` |
|---|---|
| `p` | **0800** |
| `w` | **0800** |
| `s88` | **0800** |
| `q` | **0800** |
| `q81` | **0800** |
| `x91` | **9100** |

Ровно один кандидат на представление даёт счётчик 1, остальные семь — 0, и
контроль без правила равен 1 всегда. Механизм: `nft_do_chain_bridge()` для `q`
видит `eth_hdr()->h_proto` = `8100` → `nft_set_pktinfo_unspec()` → `flags = 0`;
тогда `nft_meta_pktinfo_may_update()` входит в ветку `case ETH_P_8021Q` и читает
`veth->h_vlan_encapsulated_proto` по `mac_header+16`. После одноуровневого
снятия двухметочного кадра по этому адресу лежит **настоящий** ethertype
`0800` — отсюда «ip».

То есть: страж зовёт этот кадр «никакой» (§4), `meta protocol` зовёт его «ip»,
а стек не видит его вовсе (§7). Три разных ответа об одном пакете.

## 2. Граница `ll` — 18 у всех четырёх меченых представлений, и таблица у них одна

Сетка 36 клеток на представление, хук `bridge prerouting`, база `ll`:

| представление | живых | мёртвые |
|---|---|---|
| `p` | **23/36** | (12,4) (14,\*) (16,\*) (20,\*) (24,\*) |
| `w` | **25/36** | (10,4) (12,1) (14,1) (14,4) (16,4) (20,\*) (24,\*) |
| `s88` | **25/36** | те же |
| `q` | **25/36** | те же |
| `q81` | **25/36** | те же |
| `x91` | **23/36** | как у `p` |

Множества живых клеток `w`, `s88`, `q`, `q81` совпадают **клетка в клетку**;
`p` и `x91` — тоже между собой. Значит `0x88a8` на этой границе неотличим от
`0x8100`, а вторая метка не двигает ни одной клетки: `vlan_hlen` в коде — это
`VLAN_HLEN` = 4, а не «сколько меток в кадре».

**А вот что эти клетки пишут — разное.** Смещение базы `ll` — это координата
провода: код вычитает `vlan_hlen`, поэтому клетка `(16,2)` попадает в байт
кадра `off-4` = 12:

| клетка | на `w` (байты кадра, дифф к контролю) | на `q` |
|---|---|---|
| (16,1) | `12:08>90` — ethertype | `12:81>90` — **внутренний TPID** |
| (16,2) | `12:08>90,13:00>91` | `12:81>90,13:00>91` |
| (12,2) | `12:08>90,13:00>91` + метка вставлена на выходе (`len:60>64`) | `12:81>90,13:00>91,15:c8>64` + `len:64>68` |
| (14,2) | в кадре ничего (`wchgs=-`) | в кадре ничего |
| (12,4) | `len:60>64`, метка `9091 9293` | `len:64>68`, метка `9091 9293` |
| (20,1) | мёртва | мёртва — **настоящий ethertype лежит по смещению 20 и недостижим** |

Клетка `(16,2)` на QinQ-кадре пишет не ethertype, а TPID внутренней метки:
после записи дальняя сторона видит в байтах `9091 00c8 0800` и не снимает
ничего. Настоящий ethertype `q` — байты 16..17, это `ll`-смещение 20, а
граница — 18. Одной метки в формуле не хватает ровно на одну метку.

## 3. Страж `nh` в мосту: 14/40 против 0/40

Сетка 40 клеток, база `nh`, тот же хук:

| представление | `pkt->ethertype` | живых |
|---|---|---|
| `w` | 0800 | **14/40** |
| `q` | 8100 | **0/40** |

`nft_nh_write_ok_bridge()` переключается по `pkt->ethertype`, а `pkt->ethertype`
для моста — это `skb->protocol`, то есть `8100` у `q`. Ветви `ETH_P_8021Q` в
переключателе нет, `default → false` — и отказывают **все** сорок клеток,
включая `(8,1)`, которую ip-семейство на том же кадре разрешает.

## 4. `meta protocol` перед записью открывает страж — и сдвигает запись на 4 байта назад

То же правило, но перед записью стоит `meta protocol` + `cmp ne 0xffff`
(условие всегда истинно, важен сам вызов):

| представление + форма правила | живых |
|---|---|
| `w`, только запись | **14/40** |
| `w`, meta + запись | **14/40** |
| `q`, только запись | **0/40** |
| `q`, meta + запись | **12/40** |

Для `q` это снимает отказ всех сорока клеток: `nft_meta_get_eval()` вызывает
`nft_meta_pktinfo_may_update()`, тот находит настоящий IPv4-заголовок
(`nhoff = VLAN_HLEN + skb_network_offset = 4`) и присваивает
`pkt->ethertype = 0x0800`. Страж, стоящий **после** этой экспрессии в той же
цепи, видит уже не `8100`, а `0800` — и берёт список ip4.

Не 14, а 12 потому, что две клетки списка читают пакет: `(0,2)` сверяет
записанный байт с байтом по `skb_network_offset+0` (это `TCI2`, `00`, а не
`45`), а `(8,2)` — с байтом по `+9` (это младший байт `id`, `34`, а не `11`).

И главное: **origin записи не поехал вместе с `nhoff`**.

| клетка | что пишет на `q` | что это за поле |
|---|---|---|
| (8,1) | байт 22 кадра: `12`→`90` | **id**, старший байт — не ttl |
| (8,2) | байты 22..23: `12 34`→`90 11` | id целиком |
| (0,2) | байты 14..15: `00 c8`→`45 91` | TCI внутренней метки |

Чтение и запись в одном и том же коде разъезжаются на `pkt->nhoff`: у чтения
`offset = skb_network_offset(skb) + pkt->nhoff`, у записи `offset =
skb_network_offset(skb)`. После того как `meta` починила `nhoff = 4`,
`@nh,8,1` **читает** ttl правильно и **пишет** в id. Сторона чтения в этом ходе
не измерена — записана долгом.

## 5. Дорога наружу: два бита, а не один

Кадр `w` (одна метка `8100/0064` в байтах), правило на `bridge prerouting`,
три состояния возможностей выходного порта `r1` и пять записей:

| возможности `r1` | запись | провод | дальний тап |
|---|---|---|---|
| CTAG_TX=1, STAG_TX=1 | контроль | 60, метки нет | 60 |
| | (12,2)=`8100` | 60 | 60 |
| | (12,2)=`88a8` | **60** | 60 |
| | (12,2)=`0000` | 64, `0000 0064` | 64 |
| | (12,4)=`88a8 0064` | **60** | 60 |
| CTAG_TX=0, STAG_TX=1 | контроль | 64, `8100 0064` | 60 |
| | (12,2)=`8100` | 64, `8100 0064` | 60 |
| | (12,2)=`88a8` | **60** | 60 |
| | (12,2)=`0000` | 64, `0000 0064` | 64 |
| | (12,4)=`88a8 0064` | **60** | 60 |
| CTAG_TX=0, STAG_TX=0 | контроль | 64, `8100 0064` | 60 |
| | (12,2)=`8100` | 64, `8100 0064` | 60 |
| | (12,2)=`88a8` | **64, `88a8 0064`** | 60 |
| | (12,2)=`0000` | 64, `0000 0064` | 64 |
| | (12,4)=`88a8 0064` | **64, `88a8 0064`** | 60 |

Читается так: `validate_xmit_vlan()` вставляет метку в кадр, только если
`vlan_hw_offload_capable(features, skb->vlan_proto)` ложно, а эта функция знает
**два** бита — `NETIF_F_HW_VLAN_CTAG_TX` (бит 7) для `0x8100` и
`NETIF_F_HW_VLAN_STAG_TX` (**бит 45**) для `0x88a8`. У veth оба бита в
`VETH_FEATURES` по умолчанию. F37 снимал только бит 7 — состояние B, и в нём
запись `(12,2)=0x88a8` **не оставляет на проводе ничего**: метка остаётся в
метаданных и умирает вместе с ними. Увидеть 0x88a8 можно только в состоянии C —
когда сняты оба бита; тогда на проводе `88a8 0064` и дальняя сторона снимает
её обратно в 60 байт.

Три состояния подтверждены чтением самих возможностей из загрузки
(`F561 SET`/`F561 FEAT`: `ctag_tx`, `stag_tx`, `stag_rx` до и после каждого
изменения, `F_UNSUPPORTED=0`, `F_WISH=0`, и восстановление в конце).

## 6. Приёмная сторона: снимается ровно одна метка

Та же отправка без моста (`i0 → i1`), две отдельные загрузки одного режима:

| представление | провод | дальний тап | IpInReceives |
|---|---|---|---|
| `p` | 60 | 60 | **+1** |
| `w` | 64 | 60 | 0 |
| `s88` | 64 | 60 | 0 |
| `q` | 68 | **64, `8100 00c8 0800…`** | **0** |
| `q81` | 68 | **64, `8100 00c8 0800…`** | **0** |
| `x91` | 64 | 64 | 0 |

Обе загрузки дают одну и ту же таблицу. Механизм: `skb_vlan_untag()` в самом
начале возвращает skb без изменений, если `skb_vlan_tag_present(skb)` уже
истинно, — а первый pop его и выставляет. Второй pop в том же skb невозможен,
поэтому QinQ-кадр теряет внешнюю метку, а внутренняя остаётся в байтах, и
`skb->protocol` навсегда остаётся `0x8100`: до `ip_rcv` он не доходит.

Два «нуля» в последней колонке означают разное, и это стоит держать врозь:
у `q` стек не получает кадр, потому что его протокол `8100`; у `w` и `s88`
стек получает кадр, но выбрасывает его как `PACKET_OTHERHOST` — vid 100 без
vlan-устройства (это измерено в F38 парой `s14_0` / `s14_99`: tci=0 → +2,
tci=100 → +0). Мой прогноз P9 говорил «w и s88 дадут +1» — **опровергнут**.

## 7. Что остаётся на проводе после моста

Тот же QinQ-кадр, прошедший через мост, на выходном порту `r1` — 64 байта
`[dst][src][8100][00c8][0800][ip]`: внешняя метка снята в метаданные, а на
выходе не вернулась (STAG-capable), внутренняя осталась в байтах. Дальняя
сторона снимает её как обычную `0x8100` и получает 60 байт. То есть один и тот
же кадр за один проход через мост теряет одну метку, а за приём — вторую, но
двумя разными механизмами и в двух разных местах.

## 8. Шум, который я не объясняю

Секция `far` в батарее стоит первой, сразу после подъёма интерфейсов, и её
`IpInReceives` не сходится ни с моделью, ни между загрузками: `rep1` — `p`=3,
`rep2` — `p`=1 и `w`=2. Тот же режим, запущенный один в свежей загрузке,
дважды даёт ровно модель: 1, 0, 0, 0, 0, 0. Записано как есть: шум окна после
загрузки, а не поведение ядра; вердикты §6 взяты из отдельных загрузок, байты
во всех четырёх прогонах совпадают.

## 9. Ingress: 40/40 у обоих кадров и те же четыре байта

netdev ingress на порту `s1`, база `nh`:

| представление | живых | (8,1) пишет |
|---|---|---|
| `p` | **40/40** | байт 22 кадра — ttl (`40`→`90`) |
| `q` | **40/40** | байт 22 кадра — **id**, старший байт (`12`→`90`) |

Ingress возвращает `true` до всякого переключения, поэтому «принято» здесь не
значит ничего. Разница в том, что IPv4-заголовок у `p` начинается с байта 14,
а у `q` — с байта 18: одна и та же клетка пишет в разные поля, и ни один
счётчик этого не показывает.

## 10. Что это меняет, а что нет

**Не меняет F29–F38.** Ядро то же, кода не касались; таблицы §2 и §3 сходятся
с прежними измерениями там, где они пересекаются (`w` 25/36 и 14/40 — это
F36 и F38 клетка в клетку).
**Не регрессия.** Ни одного нового ядра; differ собран из differ560.
**Не уязвимость.** Правило ставит root в начальном user ns; следствия —
молча не выполненная запись, кадр, ушедший без метки или с чужой меткой, и
запись на 4 байта раньше поля, которое она называет.
**Меняет формулировку.** Белый список стража выбирается полем, которое
заполняет приёмный путь (`eth_hdr()->h_proto`) и которое может переписать
другая экспрессия в той же цепи (`pkt->ethertype`); «дорога наружу» зависит от
**двух** бит возможностей, и второй из них в проекте не трогал никто; а снятие
метки одноуровневое не по замыслу, а потому что второй раз `skb_vlan_untag()`
не делает ничего.

## 11. Ошибки хода, все мои

1. **Бит `NETIF_F_HW_VLAN_STAG_TX` — 45, а не 46.** Я считал значения enum
   вручную и не учёл, что алиасы (`NETIF_F_TSO_BIT = NETIF_F_GSO_SHIFT`,
   `NETIF_F_GSO_LAST = NETIF_F_GSO_ACCECN_BIT`) новых значений не занимают.
   В состоянии «сняты оба бита» снимался 46 — это `STAG_RX`, — и состояние C
   вело себя ровно как B. Поймало измерение: `(12,2)=0x88a8` не дало метки там,
   где по модели обязано было. Весь ход перезапущен; номер бита теперь
   выводится из enum скриптом и сверяется верификатором.
2. **Неинициализированные `cw`/`cr` в приборе**: у плеча без базовой линии в
   поле `wchgs`/`rchgs` печаталась строка предыдущего плеча (при `wchg=0`).
   Нашёл, читая контроль `ll.q` в дыму; исправлено до того, как хоть одно
   число попало в отчёт; батарея перезапущена.
3. **P9 опровергнут наполовину**: одиночные метки (`w`, `s88`) до `ip_rcv`
   не доходят — vid 100 без vlan-устройства даёт `PACKET_OTHERHOST`. Байты
   дальнего тапа я предсказал верно, счётчик — нет.
4. **P8 опровергнут во второй половине**: метка `0x88a8` доходит до провода,
   но не до `ip_rcv` — по той же причине (vid 100). Переключатель доставки —
   TCI, и это F38 измерил парой `s14_0`/`s14_99`.
5. `pkill -f "f39_run.sh full"` убил мою же оболочку: шаблон совпал с
   командной строкой самого `pkill`. Пять минут хода.
6. Верификатор дважды был неверен раньше, чем полезен: читал поле `ctl["w"]`,
   которого в логе нет (печатается `whex`) — `KeyError`; и сравнивал 32 символа
   с 24-символьным префиксом (`[:24]` против строки из 32) — три красные
   проверки на верных данных.
7. Проверка «каждый режим завершился с 0» ждала маркеры `MODE_EXIT f561far=…`
   в батарее, где режим один (`f561`) — шесть красных проверок на верных данных.
8. `acks=0` почти на всех плечах этой батареи: 250-мс окно ACK не успевает под
   нагрузкой TCG. Урок F38 («правило без ACK могло не встать») здесь не
   применим напрямую, поэтому установка доказывается счётчиком, а не ACK —
   и это сказано в отчёте явно, а не замолчано.

## 13. Что не измерено, прямо

- Только `7.3.4-T558`; семейства `bridge` и `netdev`, один хост, одна veth-пара.
- **Сторона чтения `@nh` после `meta`** (`nhoff=4`) не измерена: в §4 измерена
  только запись; утверждение о расхождении чтения и записи — из кода.
- `0x9100` — просто неизвестный TPID; QinQ с `0x88a8` и внутри, и снаружи не
  собирался (`q81` — это `8100`+`8100`).
- vlan-устройства нет: `vlan_do_receive()` с `vlan_proto=0x88a8` не проверялся.
- GSO/`CHECKSUM_PARTIAL`, записи с пересчётом контрольной суммы, `@ih` на
  QinQ-кадре, IPv6 и ARP в этом конверте — не тронуты.
- Распределения, где VLAN-биты `=m`/`=y`, не загружались.
- `IpInReceives` в первой секции батареи шумит (§8).
- Не уязвимость: правило ставит root в начальном user ns.
