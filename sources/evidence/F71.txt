F71 -- the skb behind skb_condense()'s first clause, measured at the function

Kernel 7.3.4-T563 (no new build). Instrument: three netns on IPv4, the same
veth pairs as before, a sender and a receiver in their own namespaces, and
seven kprobes with fetchargs at the field offsets pahole reads out of this
kernel's own DWARF (len 112, data_len 116, tail 188, end 192, truesize 216,
flags 126). The receiver now has TWO sockets, 5000 plain and 5001 with
UDP_GRO, drained and measured per port, so the same datagrams can be delivered
whole or cut into pieces at will.

1. The skb that reaches the branch with data_len > 0 is the aggregate built by
   rx-udp-gro-forwarding at the sender, delivered whole to a UDP_GRO socket.

       f593enq:  len=3072 dlen=2560 tail=556 end=704 ts=7680 fl=0
       f593cond: len=3072 dlen=2560 tail=556 end=704 ts=7680 fl=0

   Six datagrams of 512 bytes: one enqueue, one call of skb_condense(), and the
   early return is taken by the first clause alone -- 2560 bytes of fragments
   against 148 bytes of tailroom. __pskb_pull_tail is not called and the queue
   keeps the whole 7680. On the plain socket the same six datagrams are cut by
   skb_segment() into six skbs of 1280 and the branch fires six times.

2. The comparison is with the HEAD's tailroom, so the boundary is a property of
   the buffer, not of the traffic. Three head sizes give three boundaries, each
   pinned to the byte (two attempts per arm, two boots; all four measurements of
   each cell identical):

       head 512:  end 704  tail 556  room 148   147,148 pull   149 returns
       head 200:  end 384  tail 244  room 140   139,140 pull   141 returns
       head 1200: end 1728 tail 1244 room 484   483,484 pull   485 returns

   `data_len == end - tail` is not greater, so it pulls: __pskb_pull_tail()
   copies exactly data_len bytes into the tail room (eat = tail + delta - end
   = 0, no expansion) and the last line of skb_condense() reprices the skb to
   SKB_TRUESIZE(end) -- 1280, 960, 2304. One byte more and the queue keeps
   2240, 1920, 3584.

3. A passive AF_PACKET socket on the forwarding device changes that number.
   With the parent's y1/y2 taps open, the same 512+147 pair never pulls:
   dev_queue_xmit_nit() clones the skb, skb_cloned() is the second clause, and
   it returns before __pskb_pull_tail(). Measured, four times each:

       taps closed:  cloned 0, skb_clone 0 calls, pull 1 (eat=147), charge 1280
       taps open:    cloned 1, skb_clone 5/2 calls, pull 0,          charge 2240

   The payload delivered to the application is identical (659 bytes in both
   cases); only the socket's memory account differs, by the price of one
   datagram. This is the third observer effect this instrument has run into --
   the first was that the same tap disables GRO at the receiver -- and it is
   the first one that moves a number rather than a shape.

4. UDP_GRO does nothing for a fraglist aggregate, and the source says why:
   udp_unexpected_gso() refuses SKB_GSO_FRAGLIST unless the socket has
   ACCEPT_FRAGLIST, and UDP_GRO sets only ACCEPT_L4. ACCEPT_FRAGLIST is set by
   udp_allow_gso(), called from vxlan, geneve and bareudp only. Measured: six
   enqueues, six calls, skb_segment_list once, charge 7680 -- identical to a
   plain socket. The aggregate that IS delivered whole is the one from the
   linear door, and it arrives as one datagram of 3072 bytes.

Nothing here is a kernel bug: it is the documented price of a memory-pressure
branch and of a socket option. What is worth knowing is which of the three
things decides the queue's byte account -- the device bit at the sender, the
socket bit at the receiver, or the existence of a monitor on the wire -- and
that none of the three is visible to a rule that reads the packet.


===== SUMMARY.md =====
# F71 — the first clause of `skb_condense()`: a byte boundary, and a second clause standing in front of it

Turn 593. Kernel `7.3.4-T563` (`1efbc957…2033`), **no new build**. Instrument
`differ593`, mode `gro`: **18 arms × 2 attempts × 2 boots = 72 attempts**, all
with the marker window intact.

The debt, in F70's own words (§8): *«Все три клаузы раннего выхода
`skb_condense()` в этих плечах недостижимы: `data_len == 0` проскакивает блок
целиком.»* 36 attempts of F70 called `__pskb_pull_tail` zero times, and the
reason was not the clause but the skb: no skb with `data_len > 0` ever reached
the queue gate. This turn builds one.

## 0. What the source says, and what the arms were built from

Three readings decide everything (`research/predictions_593.md` §1, frozen
before the first boot):

1. **`udp_unexpected_gso()`** (`include/linux/udp.h:214`) calls a packet
   unexpected GSO if `gso_type` has `SKB_GSO_FRAGLIST` and the socket lacks
   `ACCEPT_FRAGLIST` — and **`UDP_GRO` sets only `ACCEPT_L4`**
   (`net/ipv4/udp.c:3019`). `ACCEPT_FRAGLIST` is set by `udp_allow_gso()`, whose
   only callers in this tree are `vxlan_core.c`, `geneve.c` and `bareudp.c`.
   So a fraglist aggregate **cannot** be delivered whole to a user UDP_GRO
   socket: the socket's GRO bit is blind to it.
2. **`skb_gro_receive()`** (`net/core/gro.c`) merges the *linear* GRO door
   (`rx-udp-gro-forwarding`, `sk == NULL`) into a **frag_list** or into page
   frags, and does `p->data_len += len` where `len = skb_gro_len()`, the
   **payload**. Such an aggregate has `data_len > 0`, `gso_type =
   SKB_GSO_UDP_L4`, and a UDP_GRO socket does accept it — that is the skb
   clause 1 needs.
3. **`skb_condense()`** (`net/core/skbuff.c:7131`) compares `data_len` with the
   **head's tailroom** `end - tail`, and `__pskb_pull_tail(skb, data_len)` with
   `data_len == end - tail` needs no expansion (`eat = tail + delta - end = 0`).

The instrument is F69/F70's three-netns IPv4 path unchanged, with a new
receiver: **two sockets**, 5000 plain and 5001 with `UDP_GRO`, each drained and
measured per port. Seven kprobes, with the fetchargs offsets pahole reads out of
the booting vmlinux (`len 112, data_len 116, tail 188, end 192, truesize 216,
flags 126`):

```
p:f593cond  skb_condense                       len dlen tail end ts fl
p:f593enq   __udp_enqueue_schedule_skb          len dlen tail end ts fl   <- THE GATE
p:f593pull  __pskb_pull_tail                   eat=%si
p:f593seg   skb_segment_list
p:f593trim  ___pskb_trim
p:f593clone skb_clone
p:f593exp   pskb_expand_head
```

The gate probe is the turn's own addition: without it the geometry of a skb is
only visible when the queue is above half a buffer — and half the arms are
below it on purpose.

## 1. The skb that clause 1 needs: one enqueue, `data_len` 2560

Six datagrams of 512 bytes through the linear door, delivered whole to the
5001 socket, queue above half (filler 16 × 1280 = 20480, `sk_rcvbuf` 38400):

```
f593enq:  len=3072 dlen=2560 tail=556 end=704 ts=7680 fl=0
f593cond: len=3072 dlen=2560 tail=556 end=704 ts=7680 fl=0     <- one call
```

- **one** enqueue and **one** `skb_condense()` call, against six and six on the
  plain socket for the same six datagrams;
- `data_len` 2560 = 5 × 512: the merged datagrams contribute **payload only**,
  as `skb_gro_receive()` writes it;
- `end - tail` = 704 − 556 = **148**, so `data_len > room` and the early return
  is taken **by clause 1 alone** (`fl = 0`: not cloned, and `trim` = 0);
- `__pskb_pull_tail` is not called; the queue gains **7680** — the same number
  it gains below half a buffer (`g_pg6_lo`: 0 calls of `skb_condense`, charge
  7680). Condense cannot touch this skb.

What the socket receives is one datagram of **3072** bytes (`hl1=512,3072`),
i.e. the whole aggregate, not six datagrams.

## 2. The boundary is the head's tailroom, and it is pinned to the byte

A second datagram makes `data_len` a number I can choose. Three head sizes,
three tailrooms, three boundaries:

| head | `end` | `tail` | room | pulls at | returns at | charge after the pull |
|---|---|---|---|---|---|---|
| 512 | 704 | 556 | **148** | 147, **148** | **149** | **1280** = 704 + 576 |
| 200 | 384 | 244 | **140** | 139, **140** | **141** | **960** = 384 + 576 |
| 1200 | 1728 | 1244 | **484** | 483, **484** | **485** | **2304** = 1728 + 576 |

The equality is **not** greater: `data_len == end - tail` pulls (the kernel's
`>`), one byte more returns. `eat` equals `data_len` exactly (147, 148, 139,
140, 483, 484), and the charge after the pull is `SKB_TRUESIZE(end)` — the last
line of `skb_condense()` doing its documented work on a skb whose fragments were
just freed.

Three different rooms give three different boundaries. The comparison is with
the head's tailroom, which depends on the head's buffer — not with a constant,
and not with the datagram's size.

## 3. Above half costs **less** than below half

| arm | filler | `data_len` | `skb_condense` | pulled | charge |
|---|---|---|---|---|---|
| `g_t512_lo` | 0 | 148 | 0 calls | — | **2240** |
| `g_t512_148` | 16 | 148 | 1 call | 148 bytes | **1280** |

The same two datagrams (512 + 148). Below half the socket is charged 2240, above
half **1280**: the branch exists to *reduce* memory, and here it cuts the charge
by 960 bytes — exactly the price of the second datagram. The inversion is the
whole point of the branch, and now it is a cell rather than a comment.

## 4. The number I predicted was wrong: the merge is a frag_list, and it charges the whole truesize

Predictions §2 said the linear door would put the merged payloads into **page
frags**, where `delta_truesize = skb->truesize - SKB_DATA_ALIGN(sizeof(struct
sk_buff))` = `ts − 256`, giving 6400 for six datagrams. Measured **7680**:

```
F593 EQ|n=1|ts=7680|dlen=2560|len=3072|tail=556|end=704|fl=0
```

7680 = 6 × 1280 — the **sum of full truesizes**, which is the `merge:` branch of
`skb_gro_receive()` (the one that links the skb into `frag_list` and sets
`delta_truesize = skb->truesize`). The page-frag branch is guarded by
`else if (skb->head_frag)`, and on this veth `head_frag` is **0**: byte 126 bit
5 is clear in every one of the 66 enqueue records each boot printed (and in the
62 condense records), so `fl` is only ever 0 or 1 — only the `cloned` bit moves. So P2's mechanism is refuted by the measurement it
was built to predict, and with it the absolute numbers of P3, P4, P6 and P7.

The same pair of datagrams shows it directly: 1280 + 960 = **2240** (the 148-byte
tail's own truesize is 960, `end` 384), not 1280 + (960 − 256) = 1984.

## 5. Clause 2 stands in front of clause 1, and my own tap is its switch

The first smoke of this turn (taps open, as every instrument since F63 has had
them) showed `fl = 1` and `pull = 0` on the arm that should have pulled. Byte 126
bit 0 is `cloned`, and `skb_cloned()` is the *second* clause: it returns before
`__pskb_pull_tail` ever runs. Why is the head cloned? Because the parent's
`y1`/`y2` AF_PACKET taps call `dev_queue_xmit_nit()`, which clones the skb it
sees — F63's lesson («мой же тап выключал измеряемый GRO»), with a second
consequence nobody had measured: **the tap also blocks the pull**.

Two arms differ in nothing but the tap:

| arm | taps | cloned at the gate | `skb_clone` calls in the window | `pull` | charge |
|---|---|---|---|---|---|
| `g_t512_147` | closed | **0** | **0** | **1** (`eat=147`) | **1280** |
| `g_t512_147t` | open | **1** | 5 / 2 (both boots) | **0** | **2240** |

Four measurements of each cell, two boots, identical. So a *passive* monitor
changes the receiving socket's byte account — not the payload, not the delivery,
only the charge — by making `skb_cloned()` true. That is the third time in this
project that an observer changed the thing observed; this time it changes a
number that a rule or an accounting layer would read.

## 6. The fraglist door and the socket's GRO bit: no effect at all

| arm | door | socket | enqueues | `skb_segment_list` | delivered to the app | charge |
|---|---|---|---|---|---|---|
| `g_fl_gro` | fraglist | **UDP_GRO** | **6** | **1** | 6 × 512 | 7680 |
| `g_fl_pl` | fraglist | plain | 6 | 1 | 6 × 512 | 7680 |
| `g_pg_pl` | linear | plain | 6 | 0 | 6 × 512 | 7680 |

The UDP_GRO socket does nothing for a fraglist aggregate — P1, and it is the
reading of `udp_unexpected_gso()` confirmed by the counters, not by the source
alone. The opposite case is just as sharp: the *linear* door's aggregate on the
plain socket is cut by `skb_segment()` (`seg = 0`), on the GRO socket it is not
cut at all (`seg = 0`, one enqueue). One device bit at the sender and one socket
bit at the receiver decide whether the same six datagrams arrive as six skbs of
1280 charged bytes or as one skb of 7680 — and the rule in the middle sees the
same bytes either way.

## 7. The single datagram: no aggregate, no clause

`g_pg1_gro`: one datagram of 512 through the linear door — `dlen = 0`, one
enqueue, one condense call, charge 1280. GRO strips GSO from a one-segment
packet (F66 P8), so there is no aggregate to have fragments.

## 9. My errors this turn

1. **The gate probe read the wrong register.** `__udp_enqueue_schedule_skb(sk,
   skb)` — skb is `%si`, but I copied `%di` from `skb_condense(skb)`. The first
   smoke printed `len=141084192 dlen=4279304192`, which are fields of a
   `struct sock`. Fixed; the kernel's echo of the definition now says `%si`.
2. **The truesize model of the paged path was wrong** (§4): I predicted the
   page-frag branch and charged `ts − 256` per merge. The measurement refuted
   it in the first smoke.
3. **I did not see clause 2 coming.** The arms were designed as if clause 1
   decided; the first smoke showed `pull = 0` on the arm that should pull, and
   only then did I look at the flag byte. The tap arm exists because of that
   error.
4. **The instrument's own expectations were refitted after two smokes**
   (exp_charge 6400/1984/1664/4608 → 7680/2240/1920/3584). That is instrument
   calibration on smoke runs, before the measured boots; the *predictions* file
   was not touched, and its refuted numbers stay in the table above.
5. **The parser crashed twice** — a missing ARM block (a dropped attempt) and a
   missing log file — and had one hole (the determinism diff compared the `i`
   and `att` fields, so every attempt looked different from every other). All
   three were found by `verify593_selftest.py`, not by me reading it.
6. F70's verifier parsed the `SEQ` line of every attempt and **never checked
   it** (`grep seq tools/verify592.py` — one definition, one append, no read).
   This turn's geometry line (`EQ`/`CQ`) is checked record by record, which is
   why the gate probe was added at all.

## 10. What is not measured, plainly

- **Clause 3** (`!skb_frags_readable`) never fires and cannot be distinguished
  from a pass here: no skb in this topology carries `SKBFL_PURE_ZEROCOPY`.
- **The page-frag branch of `skb_gro_receive()`** is never taken, because
  `head_frag` is 0 on every skb this veth delivers (bit 5 of byte 126 clear in
  all records). On a NIC whose RX skb is `head_frag`, the same merge would
  charge `ts − 256` per datagram, which is the number P2 predicted.
- **Partial pulls** (`__pskb_pull_tail` with `eat` smaller than `data_len`, from
  a caller other than condense) are unreachable by construction: the clause
  refuses exactly those.
- **The clone counts** (5 in rep1, 2 in rep2 on the same arm) are a race between
  the tap's drain and the burst; only "more than zero" is claimed, and the
  number is printed rather than explained.
- 200-byte heads were measured on the 704-byte chunk; the boundary 140 is that
  chunk's tailroom, not a property of 200.
- IPv6, TCP, tunnels, `CHECKSUM_COMPLETE` and a real NIC are not touched this
  turn.

## 11. What this changes in the earlier findings

- **F70 §2** — «голова агрегата приходит на вход уже линейной» — holds for the
  fraglist door *after the receiver cut it*. On the linear door with a UDP_GRO
  socket the same traffic arrives as **one** skb with `data_len = 2560`, and
  clause 1 refuses it. Both statements are true; they are about different skbs.
- **F69's price ladder** `(2k−1)·s` is the price of the *segmented* burst. The
  whole-delivered aggregate is charged `k·s` — 7680 against 7680 in this
  topology (identical here, for two different reasons: the fraglist head's
  `(2k−1)` is condensed to one, the whole aggregate's `k` is not condensed at
  all).
- **F63's tap lesson** gets a second half: the tap disables GRO at the receiver
  *and* makes the skb cloned, so it disables the condense pull as well, and the
  queue's byte account changes by the price of one datagram. An observer that
  changes a number this project's rules can read is worth a line in every
  instrument's preamble.
